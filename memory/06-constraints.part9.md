## ⚠️ 恢复源须与实装一致（#37，2026-10-21 立规）

#36（阻断机制须可恢复）立了之后，r138 收尾发现一个更隐蔽的问题：**恢复源与实装件会静默漂移**。
`05-exec/hook_templates/*.sh`（恢复源）与 `.git/hooks/`（实装件）是两份拷贝，
而「装 hook」的真实习惯是**直接改 `.git/hooks/`**——于是模板静默过期。

**r139 实测坐实**：往 `.git/hooks/pre-commit` 追加一行 ⇒ 第 50 门（健在性自检）仍报 `8/8 通过`，
而模板与实装 `match=False`。⇒ 会出现「**自检绿但下次恢复装出旧版**」，比 hook 丢失更隐蔽。

**机器判据**：第 51 门（`r139_hook_sync.py`）逐项断言 ——
恢复源存在、实装件存在、两者 **SHA256 逐字节一致**、恢复源在 git 内被跟踪。**任一不通判红**。
且 `r138_install_hooks.py` 装完必须跑**双自证**（健在性 + 同步），两个都 rc=0 才放行。

**反向验证（r139 实测，三态）**：

| 变体 | 读数 | 判定 |
|---|---|---|
| 只改实装件（#37 要治的病） | **`s3_byte_identical` 精准 FAIL** | 有牙 |
| 模板被删（恢复源丢失） | `s1` / `s3` / `s4` 三项 FAIL | 有牙 |
| 真实状态 | 0 项 FAIL | 不冤枉 |

**设计取舍**：安装脚本「先装模板再自证」⇒ 它**必然**修掉漂移（安装=恢复=同步）。
所以第 51 门的价值不在安装路径上，而在**独立跑**时能发现「有人绕开安装脚本直接改了实装件」。

## ⚠️ 漂移须可归因（#38，2026-10-21 立规）

#37（恢复源须与实装一致）立了之后，r139 收尾发现：第 51 门能发现「模板与实装件不一致」，
但**回答不了是怎么造成的**。r140 实测量化：漂移时只有两个 sha + 两个 mtime，
无法区分「**装了旧模板**」还是「**装后被人改了实装件**」；而实装件不在 git 内，**无历史可查**。

**解法 = 安装时留印记**：`r138_install_hooks.py` 安装时把「模板 sha256 + 安装时间」写进
`.git/hooks/<name>.installed`；`r140_hook_trace.py`（第 52 门）据此做**六态归因**：

| 态 | 含义 |
|---|---|
| `IN_SYNC` | 实装件与模板一致，无漂移 |
| `DRIFT_AFTER_INSTALL` | 实装件与**印记**不同 ⇒ 装后有人改了 `.git/hooks/` |
| `DRIFT_OLD_TEMPLATE` | 实装件与印记相同、但与**当前模板**不同 ⇒ 模板被改后没重装 |
| `NO_STAMP` | 无印记（r140 之前装的）⇒ 归因不可用，须重装补印记 |
| `MISSING` / `TEMPLATE_MISSING` | 实装件 / 模板不存在 |

**机器判据**：第 52 门任一非 `IN_SYNC` 即判红；另单列「印记存在性」告警
（无印记不影响本次判定，但下次漂移将无法归因）。

**反向验证（r140 实测，四态）**：

| 变体 | 判定 | 结果 |
|---|---|---|
| 装后改实装件 | `DRIFT_AFTER_INSTALL` | 对 |
| 改模板但不重装 | `DRIFT_OLD_TEMPLATE` | 对 |
| 删印记（仍一致） | `IN_SYNC` + 无印记告警 | 对（合理优先级：无漂移就不需要归因） |
| 真实状态 | `IN_SYNC` | 对 |

**r140 自抓（#32 的直接收益）**：初版把两个归因条件**写反了**，V1/V2 全部判反 ——
`installed == stamp` 说明实装件就是当初装的模板（变的是模板），`installed != stamp`
说明实装件被改过。若不先造变体复跑，这个反态会直接写进 #38 的判据。
