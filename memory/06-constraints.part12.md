## ⚠️ 防篡改须有外部锚点（#42，2026-10-21 立规）

#41（历史须防篡改）立了之后，r143 收尾发现哈希链的天花板：**链是自洽的，伪造也可以自洽**。
r144 量化坐实：快照 + 历史**全套重写**（链自洽、末行对齐快照）⇒ H4/H5/H6 **全绿放行**——
因为三者都基于 **git 外的本地状态**，攻击者全改一遍就全绿。
（r143 的「尾部截断」同样如此——但当时被 H4/H5 间接挡住，非 H6 之功。）

**解法 = git 跟踪的外部锚点台账**：`06-benchmark/hook_install_ledger.json`。
安装时（`r138_install_hooks.py`）同步写「`lines` + `last_line_hash` + invoker + reason」。
台账在版本历史里，**改它 = 留下 git 记录**（提交者/时间可查）——这是单机文本无法自证的。

**机器判据**：第 54 门 **H7**（git 内台账 vs git 外日志对账）——
台账须有该 hook 条目、`lines` 与实际日志行数一致、`last_line_hash` 与实际末行一致。任一不符判红。

**反向验证（r144 实测，同一套伪造攻击前后对比）**：

| 攻击 | r143（无 H7） | r144（有 H7） |
|---|---|---|
| 全套自洽伪造（快照+历史重写，链自洽） | **rc=0 放行** | **rc=1 被 H7 抓住** |
| 真实状态 | rc=0 | rc=0（不冤枉） |

> 复现：`python ./_temp/v26_fullforge.py`（伪造）+ `python ./_temp/v26_probe.py`（对账验证）。

**信任根的边界（诚实声明）**：H7 的信任根是 **git 历史本身**。若攻击者能改写 git 历史
（force-push / 重写台账提交），锚点失效——但那已是另一个威胁模型（需要仓写权限 + 留 git 痕迹），
超出「改本地文件不留痕」的对抗强度。对单机文本防篡改而言，git 台账是当前可用最强锚点。

## ⚠️ 锚点对账须容窗口期（#43，2026-10-21 立规）

#42（防篡改须有外部锚点）立了之后，r144 收尾发现 H7 有误红面：**台账与安装的原子性窗口期**。
装了 hook 但台账还没提交（并行会话提交了旧台账 / 本地装完即跑门）⇒
台账 `lines` 落后实际日志 1 行 ⇒ H7 误红。r145 量化坐实（`_temp/v28_window.py`）。

**难点**：窗口期误红与真篡改的读数**一模一样**（都是 lines 不符）——
宽限必须能区分「落后的那行是谁装的」。

**解法 = 宽限判别（三条件同时满足才宽限）**：
1. 台账 `lines` == 实际行数 **- 1**（只落后一次安装）；
2. 台账 `last_line_hash` == 倒数第二行的 `line_hash`（台账完整反映到缺行之前）；
3. 缺的那行 `invoker.session` ∈ 当前进程会话集（或 git_user 匹配）——**是本会话自己刚装的**。

三条件同时满足 ⇒ H7 转 True + **显形警告**（「窗口期宽限，请尽快提交台账」），不静默；
任一不满足（缺行系外来会话 / 落后 >1 行 / 台账 hash 对不上）⇒ **维持判红**。

**反向验证（r145 实测，三态）**：

| 变体 | 读数 | 判定 |
|---|---|---|
| 窗口期（落后 1 行 + 本会话所装） | `h7=True` + 宽限警告，rc=0 | 容对 |
| 同样落后但缺行系外来会话 | **仍判红** | 不放过 |
| 真实状态 | rc=0 | 不冤枉 |

**r145 自抓（#32 的直接收益）**：前两版探针「宽限未生效」，逐层排查后确认
**判据没错，是探针造景不真实**（只改 `lines` 没改 `last_line_hash`——那是「台账损坏」态，
判红是正确行为）。真实窗口期造景必须同时对齐两个台账字段 + 用**当前进程的真实会话 ID**。
