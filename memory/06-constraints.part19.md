## 附（r260 同轮）：改文件的两条硬纪律（一手截断事故）

一手代价：Lead 一个「往报告里插一行取值命令」的脚本把该件**截断成 0 字节** —— 它写成
`io.open(P,"w").write("".join(lines))`：打开即清空，而 `join` 因数组混进一个 tuple 抛 TypeError，
于是崩在写之前。恢复靠 `git checkout HEAD --`（该件由本会话上一提交新建、开工前不存在 ⇒
恢复 = 回到自己最后提交态，不涉他人在途）。教训两条，与本卷上方四步序同级：

1. **改已有文件一律走原地替换**（edit / `r46_mark_verdict` / `handoff.py safe-edit` 等带断言入口）；
   **禁**「先以写模式打开、再在同一表达式里拼内容」。必须用脚本时顺序 = 先在内存里拼好新内容并
   断言非空 → 再原子替换（`tmp` + `os.replace`）——本仓 r114/r208 等既有件都是这个形态。
2. **写完立即复量**：`wc -c` 对预期（截断的表现是 0 或骤降），并复跑引用面判据看**分母**是否回升
   （`r52_md_claim_face_scan.py` 的数字声明总数就是「扫描面完整性」探针：本轮它从 4055（文件被截空）
   回到 4090 ⇒ 才敢认那个 `LIVE 0` 是真绿）。通用形式：**零敞口读数必须先证分母非空**（R247），
   否则「扫干净」与「扫了个空」不可分辨。
