## 1. 真缺口：`gh` 命令名被三方争夺，PowerShell 侧解析到 0 字节空壳

同一条命令 `gh`，两个解释器给出相反结论：

    # Python 侧（shutil.which 按 PATHEXT 找带扩展名的件）
    C:\Program Files\GitHub CLI\gh.EXE   size=41,483,064   => 正常

    # PowerShell 侧（Get-Command 会把无扩展名文件也当命令命中）
    C:\Users\37533\.local\bin\gh         size=0             => 裸调必炸
    PS> gh --version
    Cannot run a document in the middle of a pipeline: C:\Users\37533\.local\bin\gh

根因 = Machine PATH 里 `C:\Users\37533\.local\bin` 排在**第 20 位**，
`C:\Program Files\GitHub CLI\` 排在**第 24 位** ⇒ 空壳赢在前面。该空壳 mtime 2026-08-08 04:18:52，
0 字节、git 未跟踪、旁边还有个同样 0 字节的 `gh.txt`（无 PATHEXT 冲突，留在原地）。

第三个同名实现（本轮附带发现，比前两个更阴）：

    D:\npm-global\gh.ps1 / gh.cmd   => npm 第三方包「gh」2.8.9（不是 GitHub CLI）
    PS> gh --help      => TypeError: Cannot read properties of undefined (reading 'forEach')
    PS> gh api ...     => TypeError: Cannot read properties of undefined (reading 'options')

`D:\npm-global` 在 Machine PATH 第 43 位（排在官方 CLI 之后，本轮未遮蔽），但它证明了一件事：
**凡按裸命令名调用 gh 的判据，都可能跑到一个连 --help 都会崩的第三方包上，而它的退出码是 0。**

## 7. 网络通路两态取证（本轮推送实测，与 R151-9 / R161-2 方向相反）

推送时先按既往处方「清空代理绕行」跑，三连失败；再按反方向「显式设代理」跑，成功。逐态读数：

    git -c http.proxy= -c https.proxy= push origin main

                 Failed to connect to github.com port 443 after 21088 ms: Could not connect to server
    Test-NetConnection github.com -Port 443   => TcpTestSucceeded=False

    # 态 B：显式设代理（本轮正解）
    git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=同值 push origin main
      => rc=0   758c0ab..24e8576  main -> main（ls-remote == rev-parse）

    # 旁证（勿当直连证据用）
    Invoke-WebRequest https://github.com -Method Head   => 200   （但 netsh winhttp 显示 Direct access，
                                                           该 200 走的是 WinHTTP 自身通路，不能证伪态 A）
    Test-NetConnection 127.0.0.1 -Port 7897             => True（代理进程在听）

> **⚠️ 校正注（r163g，并行会话纠偏 + 我独立复算坐实；原文按 R241 保留不改）**
> 上文「0 字节空文件 / 空壳」的**机制表述是错的**。`fsutil reparsepoint query` 实测：
> `C:/Users/37533/.local/bin/gh` 是 **junction**（Reparse Tag `0xa000001d` = Microsoft Name Surrogate，
> 目标字节 `/mnt/c/Program Files/GitHub CLI/gh.exe` —— WSL 形态路径），`dir /AL` 亦标 `<JUNCTION>`。
> junction 的 `Get-Item .Length` 恒为 0，我把「报 0」当成了「空文件」——这是**读数字段的语义误读**。
>
> 但**结论与处置不变**，因为该 junction 在 Windows 侧根本跑不起来（独立复算，非采信任何一方叙述）：
>
>     os.path.getsize(该件)  =>  OSError WinError 1920「系统无法访问此文件」
>     目标 /mnt/c/... 在 Windows 侧存在?  =>  False（C:\mnt\... 不存在）
>     PowerShell 裸调 gh      =>  Cannot run a document in the middle of a pipeline
>
> 即「它是 junction」与「它不可用」两件事同时成立：对方纠的是**归因机制**（对，我接受），
> 而「真装件 gh 2.95.0 已登录可用 ⇒ 判定被推翻」不成立 —— 可用的是**另一个件**（Program Files 那份），
> 遮蔽问题本身是真的，重命名后 PowerShell 侧 `Get-Command gh` 从 junction 变到真实件（before/after 已实测）。
>
> **对谓词的实际修改（这才是纠偏的收益）**：旧谓词 `getsize<=0 ⇒ 空壳` 双向失真 ——
> 会把**指向有效的合法 junction** 误判成空壳，又会把 **size>0 但跑不起来**的真坏件放过去。
> 现改为判**可跑性**：按 PATH 解析到的那个件真跑一次 `--version`，跑不起来才 FAIL；
> 并新增 `is_reparse()` 把「是重解析点」作为诊断信息显形（不参与判据）。四腿自证仍 4/4。

结论（#46 适用边界）：「清空代理」与「设代理」都不是恒真处方 —— 同一仓同一远端在 10:1x 与 11:0x
两个时段给出相反结果，属网络环境漂移。故落探针 `05-exec/r163_net_path_probe.py`（两态各跑一次再定方向），

## 16. 判据与现实漂移：Turnstile 明明在生产用着，第 65 门却报「凭据缺口」

本轮开局复查名册，发现第 65 门仍把 `Cloudflare-Turnstile` 判为 **`GAP_CRED`**——理由是
「本机 env 里没有 `CF_TURNSTILE_SITE_KEY` / `CF_TURNSTILE_SECRET_KEY`」。

**而它上一轮刚刚在 production 上拦住了三个写接口。**

### 16.1 根因：把「凭据的仓库位置」写成了「凭据有没有」

Turnstile 的凭据**本来就不该在本机 env**：widget 的 sitekey/secret 由 Cloudflare 账号持有，
secret 的正确归宿是 Pages secret。用「本机有没有这个 env」当判据，等于**用错误的仓库地址判断文件是否存在**。
结果就是：工具用得越好，判据越说它缺东西 —— 这是最难发现的一类假红（它不会让门禁变绿，只会让人对红麻木）。

### 16.2 修法

判据改为「**Cloudflare 账号下是否真有 widget**」（`GET /accounts/<id>/challenges/widgets`）：

| 修前 | 修后 |
|---|---|
| 查 `os.environ` 里有无 `CF_TURNSTILE_*` | 查 Cloudflare API 有无 widget |
| 生产已启用 ⇒ 仍报 `GAP_CRED`（假红） | 读实测 widget 数（取值 `python 05-exec/r163_free_tools_face.py`，实测 **1 个**，sitekey `0x4AAAAAA…`）⇒ `READY` |
| 凭据位置写死在探针里 | `judged_by: cloudflare_widget_exists（不是本机 env）` 显式声明判据来源 |

读数变化：**`GAP_CRED` 3 → 2**（只剩 Resend / Upstash 两个真外部凭据缺口），`READY` 5 → 6。

### 16.3 自证（f1e）与它踩的两个坑

新增腿 `f1e_turnstile_judged_by_widget_not_env`，断言两件事：
① 探针**源码里不得出现**那两个 env 名（防判据退回「查本机 env」）；
② 有 widget 时必须 `READY` 且必须带具名 `judged_by`（区分「真读过」与「没读过」）。

这条腿自己踩了两个坑，都当场修了：

1. **首版写成 `... and os.environ.get(...) is not None or True`** —— 尾部 `or True` 让它恒真，
   等于**没牙**。这正是本仓反复记录的「断言写了但没咬人」形态。

## 17. 比假红更危险的一处：**反向假绿**（R2 缺口凭空蒸发）

§16 修的是「工具在用、判据说它缺」的假红。同一轮稳定性复验又抓到一个**方向相反**的缺陷：
某次连跑里 `GAP_SERVICE` 消失、`READY` 从 6 跳到 7 —— **R2 明明未开通，却被读成可用**。

### 17.1 根因：rc==0 不等于服务可用

判据原先只看子进程退出码（`rc == 0 ⇒ ready`）。而 wrangler 存在**rc=0 但打的是帮助/告警文本**
的形态（R151-8 家族）——抖动一次，`r2 bucket list` 就成了 rc=0 的非桶清单输出，判据当场被骗。

    d1    成功回 JSON 数组（含 name）        pages  成功回表格（含 'Project Name'）
    r2    成功回 'Listing buckets...'      workers 成功回 JSON 信封（success + result）

### 17.2 修法：判据从「看 rc」升级为「看形状」

抽出纯函数 `classify_service(name, rc, blob)`，按**输出形状**归类：
形状不符 ⇒ `not_probed`（没读到），**不得冒充 ready**。
同时修掉一个结构性假绿：聚合层原先只看 `not_enabled`，若某服务抖成 `not_probed` 顶层仍判 READY；
现改为**任一服务非 ready，顶层即不判 READY**（具名 `services_not_ready`），
再由 `probe_wrangler(service)` 按自己那一项精确分流（f1c 已锁「不连坐」）。

workers 项顺带换通道：原用 `deployments list --name __probe__`（占位名必失败，恒 not_probed）；
改走只读 API `GET /accounts/<id>/workers/scripts`，形状可直接校验 ⇒ 它重新拿到真实判定。

### 17.3 自证 16/16（含变异对照）

新增 6 条腿 + 1 条变异腿（腿数取值：`python 05-exec/r163_free_tools_face.py --selftest`，实测 **16/16**），其中三条是这次事故的直接对账：

## 21. Upstash 的落点结论：**没有**（本轮取证 + 一次失败实验）

r165 给 Resend 找到落点后，矩阵只剩 `Upstash-Redis` 一项零引用。本轮专门为它找真实场景，
结论是**本仓没有值得接它的地方**—— 但这个结论是查出来的，不是想当然的。

### 21.1 候选一：`r126_tag_closure.py` 的 query 向量缓存（台账 R126-4）

台账写着「每次跑要重新 encode 279 个 query，单跑约 40 秒」（题面数取值：`python 05-exec/r126_tag_closure.py` 实测输出 `题面=279`）。**实测推翻这个前提**：

| 指标 | 实测 | 台账写的 |
|---|---|---|
| 全脚本耗时 | **4.1s**（取值：本机 Stopwatch 实测 `python 05-exec/r126_tag_closure.py`）| 约 40s（差约 10 倍）|
| encode 累计（279 题）| 1.88s | — |
| route() 累计 | 2.07s | — |
| **query 去重后** | **276 / 279（重复率 1%）** | — |
| 同题二次 encode | 0.0038s | — |

⇒ 重复率仅 1%，缓存最多省 3/276 ≈ 1% 的时间。**接入 Upstash 是负收益**
（还要多一次网络往返 + 凭据管理）。顺带修正：台账里那个「40 秒」是过时读数。

### 21.2 候选二：门禁耗时 Top2 的缓存

68 门里最慢的是 `noise_tracked_stub`（23.1s）与 `free_tools_face`（21.8s）。逐个查：

- `noise_tracked_stub`：是**夹具**（造临时 git 仓库做断言），慢在 `git init/add/commit`。
  夹具要求**确定性**，给它上缓存反而破坏可重复性 ⇒ 不该接。
- `free_tools_face`：拆相后发现 `wrangler whoami` 单独占 **5~7s**（固定开销），
  四个服务探测因进程内缓存已是 0.00s。

### 21.3 一次失败实验（如实记录，包括回滚）

我尝试把 whoami 与四个服务探测并行，预期把 21.8s 压到 ~8s。**结果反而劣化**：

    改后：BROKEN=4 / READY=3 / 耗时 114s（比基线慢 5 倍）
    回滚后：READY=6 / 24.2s（回到基线）

已 `git checkout` 撤回该改动，仓内无残留。教训：**在没读懂为什么慢之前就「优化」，
会把一个 24s 的门变成 114s 的红**。并行不是万能药 —— 本门慢在 wrangler 进程启动的
固定开销（node + OAuth），多开几个进程只会互相抢资源。

### 21.4 结论与处方

Upstash（Redis）的价值在**跨进程/跨实例共享状态**。本仓的门禁全部是**单机进程内**计算，
且已有两层进程内缓存（`_WRANGLER_CACHE` / `bge_layer._QEMB_CACHE`），没有跨实例共享的真实需求。

⇒ **维持零引用，且明确记为「不适用」而非「待办」**。处方（若将来出现跨实例场景再接）：
真正的触发条件 = 同一个只读探测要在**多个进程/多台机器**上重复跑，
且结果在分钟级内稳定（如 CI runner 与本地跑同一门）。本仓目前单机单进程，不满足。

> 元教训（接 §19）：**「没找到落点」也是一个需要证据的结论**。
> 本轮用「实测推翻台账前提 + 逐候选查慢因 + 一次失败实验」三样东西，
> 把「暂时不接」从态度变成了可复算的判断。否则下一轮还会把它当欠账重新摸一遍。

## 29. 判据自己造出假红：把「调用失败」当「取到否值」（r184）

### 29.1 现象

全量门禁报 `supermarket 脱钩`：`CF Production commit_hash 5106dac 在 lxh113377/supermarket-web 远端不存在`。
但取证后 commit **确实存在**：

    gh api repos/.../commits/5106dac   => rc=0，date=2026-10-23T06:28
    本地 git cat-file -t 5106dac       => commit（且在 main 与 origin/main 上）
    gh 限流余量                        => 4892/5000
    同一 commit 单独跑本门             => PINNED；进全量门禁跑 => ORPHAN   ← 抖动型假红

### 29.2 根因：一个布尔把两件事合并了

    def _gh_commit_exists(...):
        r = subprocess.run([...])
        return r.returncode == 0      # ← 超时/限流/网络失败/登录态抖动 全被算成「不存在」

这与我 r163 立的两条纪律直接冲突（r163 反向假绿同族、r133「别把 rc 当结论」）：
**「调用失败」与「取到否值」是两件事**，必须分开归口。判据红不一定是被检对象坏，
也可能是判据自己在抖 —— 而后者更危险，因为它会把真信号一起淹掉。

### 29.3 修法：定论式三态

    ABSENT_MARKS = ("No commit found", '"status":422', '"status": 422')
    rc == 0            -> True   （存在）
    rc != 0 且命中定论词 -> False  （确证不存在 = 真脱钩）
    其余 rc != 0         -> raise  （不可判定 = UNVERIFIED，不是 DRIFT）

另按 §9.1 改走 `shutil.which` 绝对路径 + 验非零字节（防 PATH 序漂移把真 gh 换成空壳/同名件）。

自证 **15/15 → 20/20**：新增 t16-t20，全部桩化 `subprocess.run / shutil.which / os.path.getsize`
（夹具不依赖本机是否装 gh）。其中 **t20 是变异腿**：把定论词表清空后，真·不存在也退化成
raise ⇒ 证明 `ABSENT_MARKS` 真的在决定判定，不是装饰。

### 29.4 另一条：注入面 +852 不是我造成的，也没塞假哈希

五个成员里只有 `.zcode/AGENTS.md` 是当天改的（14:28，4033B），其余四个 mtime 停在 10-20/10-21；

### 31.3 根因二：checkout 重置 mtime，让「可整改面」定义在 CI 里失真

    总量都是 3138（守恒），仅 55 处从历史面翻到可整改面

**修法**：第三级改用 **git 末次提交日**（本地实测与 mtime 同值 2026-09-24，但跨 checkout 稳定），

## 47. 我一句话「ratchet 首次转绿」是假的 —— 区间归因能搭车上调别的指标（r201）

### 47.1 后门长什么样

登记 R201-5 让 `deferred_debt_items` 1→2 后，t6 腿脆断。我按本仓设计走正规通道

接着 `ratchet_gate` 打出 **PASS**，我当场写下「ratchet rc=0 首次转绿」。

然后我去核 `overdue_debt_items` 的基线为什么从 0 变成 3 —— **那条归因不存在**（留账 37→38
只多我这一笔 deferred）。读实现才看见：

```python
        if int(cur) != args.from_v:      # 只校验被点名的那一个指标
        ...
        if int(now_v) != args.to_v:      # 只校验被点名的那一个指标
        ...
        doc["metrics"], doc["attributed_raises"] = metrics, ledger   # ← 写入全部实测值
```

即：校验是单指标的，**写入是全量的**。我只点名归因 deferred，旁观的 overdue 基线被静默
从 0 抬到 3 ⇒ 棘轮「只降不升」当场失效，且无留账、无告警。

讽刺的是 r123 件头本来就写着「新通道天然是**基线上调的后门**——若不留证件…就能把只降不升

### 47.2 修法与回滚

只改被点名的指标，其余保留基线原值；别的指标要同步上调必须各自再走一次带理由的归因
（一笔一证，不许搭车）。`--raise-baseline` 分支不受影响 —— 它由 `attribute_raise` 对全部
增长项逐一校验，本就是「一笔一证」语义。

被污染的基线用 `git checkout` 还原（overdue 3→0、deferred 2→1、留账 38→37），再用修好的
代码重做那笔合法归因 ⇒ 现在 `overdue` 基线仍 0、`deferred`=2、留账 38。
`ratchet_gate` 回到诚实红：`overdue_debt_items 实测=3 基线=0`（并行会话活债，按 R269 不代裁）。

### 47.3 t8 腿自己也错过一次，被变异测试抓出来

我给这条后门补夹具 t8「搭车守卫」。**第一版**把对照基准 `bystander0` 从「已被 t6 跑过的

### 48.2 为什么这比一般 bug 严重

`gate_run_freshness` 是**自指门**：它存在的唯一理由，就是从 CI 反过来盯「人还在不在本机跑门禁」。
而它读的那本台账，正是它自己所在的 runner 写的。一个不筛 `mode` 的 `max()` 让这条防线变成：
**只要我跑一次局部，就能让 CI 以为我在本机完整跑过并通过了。** 防别人造假的判据，被我用一次
随手调用绕过 —— 这与本门自己防的是同一件事：局部面被当成全局面。

### 48.3 修法（改判据语义，不是改我上次的调用）

`judge()` 只采信 `mode == "full"` 的本机记录：`--portable-only` 按定义跳过了全部不可移植门，
它的 PASS 不能证明任何本机专属门被执行过。缺 `mode` 字段的历史行按 `full` 处理（早于该字段
引入，向后兼容）。被忽略的局部跑若晚于采信行，会在理由里显式提示 —— 可见性优先于静默：

    [FRESH:FAIL] （注：8 条局部跑 mode!=full 已忽略，其最新一条晚于本次采信的全量跑）
    取值：`python 05-exec/r32_gate_freshness.py --json <件>`（理由行自带忽略条数）；
    台账形态取值：`python -c` 读 `06-benchmark/gate_runs.jsonl` 末 8 行的 verdict/mode 两键。
                   最近一次本机门禁未过（verdict=FAIL，0.0 天前）

取值：`python 05-exec/r32_gate_freshness.py --json <件>`、`python 05-exec/r32_freshness_fixtures.py`
（24/24，含 a13~a16 四条新腿）、`python 05-exec/r202_fixture_wiring_face.py`。

> 元教训：**凡是「读自己写的东西」的判据（自指门），必须校验读到的是不是完整面。** 台账每行都带
> mode 而判定不看 mode，等于让「跑了一部分」和「跑完了」在账本上同权。上一轮的第 76 门在管

> **局部观测不能冒充全局结论。**

### 49.2 定责：不是实现回归，是夹具陈旧

三条红腿是 P3「挂账→终局→挂账 = 1（终局清零）」、P5「挂账→终局 = 0」、M1「摘掉终局清零
⇒ P3 应变 2」。取证后确认：`r38.count_deferrals` 的实现**已在 r123 主动放弃「终局清零」口径**，
件内注释留着理由与原冲突实例 ——「终局清零会把『挂账 r49 → 执行完毕』这种真实发生过一次的
改期抹成 0，与『改期 >= 2 即 REPEAT』的规则直接冲突」，现口径 = **历史改期总数**。

夹具没跟上（它仍断言旧口径）。**因为它是孤儿，这个漂移一直没被发现** —— 这正是第 78 门
存在的理由，也是我上一轮那句「孤儿夹具比没有夹具更坏：它让人以为某行为被锁住」的实证。

### 49.3 怎么改才算「不给实现背书」

对齐夹具断言是必要的（否则挂上去就是永久红噪音），但**单纯改断言等于用测试给实现盖章**。
所以做了三件事：

1. 断言对齐当前语义（P3=2、P5=1），并在件内写明「这是口径变更，不是改测试迎合实现」；
2. **把 M1 变异腿反过来写**：从「摘掉终局清零 ⇒ 应变 2」改成「实现若退回终局清零 ⇒ P3 变 1，
   即证明该口径是承重的」。这样口径被静默改回会被立即发现，而不是被悄悄接受；
3. 把两种口径的真实分歧**登记为 R202-4（降级转长期看守）**，而不是由夹具单方面定案：
   旧口径衡量「当前这轮 treadmill 有几次」，新口径衡量「这条目一共改过几次期」；两者在
   `REPEAT_AFTER=2` 门槛下对 P3 结论**相反**（旧=不触发 REPEAT，新=触发）。改门槛会改 REPEAT
   语义、进而改棘轮基线，不是本仓一个夹具能定的。

### 49.4 连带的两次自纠（都由判据自己指出，不是我事后猜的）

① 挂上 5 个新门后再跑全量，`probe_cost_face`（第 76 门）当场 FAIL，tail 直接给出修法
（门数取自 `06-benchmark/gate_run_r202_2.json`；5 = 门 80~84，取值：`python 05-exec/run_gates.py --json <件>`）：
`r200_probe_cost_fixtures.py 静态判为联网门但 manifest 里没有实测值 ⇒ 先重跑测量器`。
照做（零网络拦截测量），新门被正确归类为 `NO_EXTERNAL_CALLS`，复跑 rc=0。**判据自己会指路，
这是第 76 门上轮立「改了联网面不重测即 MISMATCH 判红」的直接收益。**

② `r67_input_pin_fixtures` 用 `mklink /J` 建 junction（Windows 专有），故必须标
`portable=False` 并写明 `not_portable_reason` —— 否则 CI 的 Linux runner 上必假红。
