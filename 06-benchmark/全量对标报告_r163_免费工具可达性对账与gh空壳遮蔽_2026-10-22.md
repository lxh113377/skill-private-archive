## 1. 真缺口：`gh` 命令名被三方争夺，PowerShell 侧解析到 0 字节空壳

同一条命令 `gh`，两个解释器给出相反结论：

    # Python 侧（shutil.which 按 PATHEXT 找带扩展名的件）
    C:\Program Files\GitHub CLI\gh.EXE   size=41,483,064   => 正常

    # PowerShell 侧（Get-Command 会把无扩展名文件也当命令命中）
    C:\Users\37533\.local\bin\gh         size=0             => 裸调必炸
    PS> gh --version
    Cannot run a document in the middle of a pipeline: C:\Users\37533\.local\bin\gh

根因 = Machine PATH 里 `C:\Users\37533\.local\bin` 排在**第 20 位**，
`C:\Program Files\GitHub CLI\` 排在**第 24 位** ⇒ 空壳赢在前面。该空壳 mtime 2026-08-08 04:18:52，
0 字节、git 未跟踪、旁边还有个同样 0 字节的 `gh.txt`（无 PATHEXT 冲突，留在原地）。

第三个同名实现（本轮附带发现，比前两个更阴）：

    D:\npm-global\gh.ps1 / gh.cmd   => npm 第三方包「gh」2.8.9（不是 GitHub CLI）
    PS> gh --help      => TypeError: Cannot read properties of undefined (reading 'forEach')
    PS> gh api ...     => TypeError: Cannot read properties of undefined (reading 'options')

`D:\npm-global` 在 Machine PATH 第 43 位（排在官方 CLI 之后，本轮未遮蔽），但它证明了一件事：
**凡按裸命令名调用 gh 的判据，都可能跑到一个连 --help 都会崩的第三方包上，而它的退出码是 0。**

## 7. 网络通路两态取证（本轮推送实测，与 R151-9 / R161-2 方向相反）

推送时先按既往处方「清空代理绕行」跑，三连失败；再按反方向「显式设代理」跑，成功。逐态读数：

    # 态 A：清空代理（R151-9 / R161-2 登记的绕行形态）
    git -c http.proxy= -c https.proxy= push origin main
      => rc=128  fatal: unable to access 'https://github.com/.../': 
                 Failed to connect to github.com port 443 after 21088 ms: Could not connect to server
    Test-NetConnection github.com -Port 443   => TcpTestSucceeded=False

    # 态 B：显式设代理（本轮正解）
    git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=同值 push origin main
      => rc=0   758c0ab..24e8576  main -> main（ls-remote == rev-parse）

    # 旁证（勿当直连证据用）
    Invoke-WebRequest https://github.com -Method Head   => 200   （但 netsh winhttp 显示 Direct access，
                                                           该 200 走的是 WinHTTP 自身通路，不能证伪态 A）
    Test-NetConnection 127.0.0.1 -Port 7897             => True（代理进程在听）

> **⚠️ 校正注（r163g，并行会话纠偏 + 我独立复算坐实；原文按 R241 保留不改）**
> 上文「0 字节空文件 / 空壳」的**机制表述是错的**。`fsutil reparsepoint query` 实测：
> `C:/Users/37533/.local/bin/gh` 是 **junction**（Reparse Tag `0xa000001d` = Microsoft Name Surrogate，
> 目标字节 `/mnt/c/Program Files/GitHub CLI/gh.exe` —— WSL 形态路径），`dir /AL` 亦标 `<JUNCTION>`。
> junction 的 `Get-Item .Length` 恒为 0，我把「报 0」当成了「空文件」——这是**读数字段的语义误读**。
>
> 但**结论与处置不变**，因为该 junction 在 Windows 侧根本跑不起来（独立复算，非采信任何一方叙述）：
>
>     os.path.getsize(该件)  =>  OSError WinError 1920「系统无法访问此文件」
>     目标 /mnt/c/... 在 Windows 侧存在?  =>  False（C:\mnt\... 不存在）
>     PowerShell 裸调 gh      =>  Cannot run a document in the middle of a pipeline
>
> 即「它是 junction」与「它不可用」两件事同时成立：对方纠的是**归因机制**（对，我接受），
> 而「真装件 gh 2.95.0 已登录可用 ⇒ 判定被推翻」不成立 —— 可用的是**另一个件**（Program Files 那份），
> 遮蔽问题本身是真的，重命名后 PowerShell 侧 `Get-Command gh` 从 junction 变到真实件（before/after 已实测）。
>
> **对谓词的实际修改（这才是纠偏的收益）**：旧谓词 `getsize<=0 ⇒ 空壳` 双向失真 ——
> 会把**指向有效的合法 junction** 误判成空壳，又会把 **size>0 但跑不起来**的真坏件放过去。
> 现改为判**可跑性**：按 PATH 解析到的那个件真跑一次 `--version`，跑不起来才 FAIL；
> 并新增 `is_reparse()` 把「是重解析点」作为诊断信息显形（不参与判据）。四腿自证仍 4/4。

结论（#46 适用边界）：「清空代理」与「设代理」都不是恒真处方 —— 同一仓同一远端在 10:1x 与 11:0x
两个时段给出相反结果，属网络环境漂移。故落探针 `05-exec/r163_net_path_probe.py`（两态各跑一次再定方向），
并给 R151-9 / R161-2 各加 R241 校正注（原文不改写）。实测读数：

## 16. 判据与现实漂移：Turnstile 明明在生产用着，第 65 门却报「凭据缺口」

本轮开局复查名册，发现第 65 门仍把 `Cloudflare-Turnstile` 判为 **`GAP_CRED`**——理由是
「本机 env 里没有 `CF_TURNSTILE_SITE_KEY` / `CF_TURNSTILE_SECRET_KEY`」。

**而它上一轮刚刚在 production 上拦住了三个写接口。**

### 16.1 根因：把「凭据的仓库位置」写成了「凭据有没有」

Turnstile 的凭据**本来就不该在本机 env**：widget 的 sitekey/secret 由 Cloudflare 账号持有，
secret 的正确归宿是 Pages secret。用「本机有没有这个 env」当判据，等于**用错误的仓库地址判断文件是否存在**。
结果就是：工具用得越好，判据越说它缺东西 —— 这是最难发现的一类假红（它不会让门禁变绿，只会让人对红麻木）。

### 16.2 修法

判据改为「**Cloudflare 账号下是否真有 widget**」（`GET /accounts/<id>/challenges/widgets`）：

| 修前 | 修后 |
|---|---|
| 查 `os.environ` 里有无 `CF_TURNSTILE_*` | 查 Cloudflare API 有无 widget |
| 生产已启用 ⇒ 仍报 `GAP_CRED`（假红） | 读实测 widget 数（取值 `python 05-exec/r163_free_tools_face.py`，实测 **1 个**，sitekey `0x4AAAAAA…`）⇒ `READY` |
| 凭据位置写死在探针里 | `judged_by: cloudflare_widget_exists（不是本机 env）` 显式声明判据来源 |

读数变化：**`GAP_CRED` 3 → 2**（只剩 Resend / Upstash 两个真外部凭据缺口），`READY` 5 → 6。

### 16.3 自证（f1e）与它踩的两个坑

新增腿 `f1e_turnstile_judged_by_widget_not_env`，断言两件事：
① 探针**源码里不得出现**那两个 env 名（防判据退回「查本机 env」）；
② 有 widget 时必须 `READY` 且必须带具名 `judged_by`（区分「真读过」与「没读过」）。

这条腿自己踩了两个坑，都当场修了：

1. **首版写成 `... and os.environ.get(...) is not None or True`** —— 尾部 `or True` 让它恒真，
   等于**没牙**。这正是本仓反复记录的「断言写了但没咬人」形态。
2. 去掉恒真后立刻**红了**——因为断言扫全文时命中了**我自己的注释**（注释里写了变量名）。
   修法：只看代码行（剥掉 `#` 注释与三引号串），并让注释**故意不写变量名**（用字符串拼接回避）。

**变异对照**：临时往探针注入一行读 env 的代码 ⇒ `f1e` 立刻 `FAIL`（rc=1），恢复后 `8/8`。
⇒ 这条腿真会咬人，不是装饰。

### 16.4 瞬态的**真实根因**：是我自己起的 Edge 拖慢了子进程

收尾验收时本门又报 `BROKEN=1`、`READY 6→5`（缺的正是 SQLite）。连查两次最终定位：

    残留 msedge 进程 = 12（本轮为探 R2 浏览器路线起的，未清干净）
    清掉后同一命令 →  READY=6 / BROKEN=0

⇒ 不是 SQLite 坏，也不是网络抖，是**上一轮步骤留下的浏览器进程把子进程启动拖到失败**。
这类「自己污染自己的测量环境」最隐蔽：读数看起来像工具缺陷，实际是**台面没收拾**。

两条处置：
1. **收口式修法（已落地）**：把重试从 SQLite 单点上移到 `run_probes`，任何探针落 BROKEN 先重试一次；
   `note.attempts` 具名记录次数（禁把「抖了」写成「坏了」）。自证 `f1f` 用「首次 BROKEN / 二次 READY」
   的注入探针锁住该行为（`9/9`）。
2. **台面纪律**：本轮起的 Edge 实例与临时 profile 已全部清理（`msedge` 残留 0）；
   这类长驻进程属于「测量前的环境前置」，应写进跑门禁前的检查项而非事后归因。

> 追加元教训：**门禁读数也会被「我自己上一步干的事」污染**。
> 判据修得再好，如果台面上还躺着自己没关的浏览器，读出来的红也只是自找的。

> 元教训（接 §15）：**判据也会过期**。工具从「没配」走到「配好且在用」时，
> 若判据仍盯着旧位置，它就从「报警器」退化成「噪音源」。修完判据要重跑一次，
> 看它是否真的反映了现状 —— 这轮 `READY 5→6` 就是那个变化的读数。


## 17. 比假红更危险的一处：**反向假绿**（R2 缺口凭空蒸发）

§16 修的是「工具在用、判据说它缺」的假红。同一轮稳定性复验又抓到一个**方向相反**的缺陷：
某次连跑里 `GAP_SERVICE` 消失、`READY` 从 6 跳到 7 —— **R2 明明未开通，却被读成可用**。

### 17.1 根因：rc==0 不等于服务可用

判据原先只看子进程退出码（`rc == 0 ⇒ ready`）。而 wrangler 存在**rc=0 但打的是帮助/告警文本**
的形态（R151-8 家族）——抖动一次，`r2 bucket list` 就成了 rc=0 的非桶清单输出，判据当场被骗。

    d1    成功回 JSON 数组（含 name）        pages  成功回表格（含 'Project Name'）
    r2    成功回 'Listing buckets...'      workers 成功回 JSON 信封（success + result）

### 17.2 修法：判据从「看 rc」升级为「看形状」

抽出纯函数 `classify_service(name, rc, blob)`，按**输出形状**归类：
形状不符 ⇒ `not_probed`（没读到），**不得冒充 ready**。
同时修掉一个结构性假绿：聚合层原先只看 `not_enabled`，若某服务抖成 `not_probed` 顶层仍判 READY；
现改为**任一服务非 ready，顶层即不判 READY**（具名 `services_not_ready`），
再由 `probe_wrangler(service)` 按自己那一项精确分流（f1c 已锁「不连坐」）。

workers 项顺带换通道：原用 `deployments list --name __probe__`（占位名必失败，恒 not_probed）；
改走只读 API `GET /accounts/<id>/workers/scripts`，形状可直接校验 ⇒ 它重新拿到真实判定。

### 17.3 自证 16/16（含变异对照）

新增 6 条腿 + 1 条变异腿（腿数取值：`python 05-exec/r163_free_tools_face.py --selftest`，实测 **16/16**），其中三条是这次事故的直接对账：

| 腿 | 断言 |
|---|---|
| `f1g` | rc=0 但输出是帮助文本 ⇒ 必须 `not_probed`（旧式会误判 ready）|
| `f1h` | 真形状（d1 JSON / r2 'Listing buckets'）⇒ 仍 `ready`（不是一律拒）|
| `f1i` | `10042` ⇒ `not_enabled` 且带 code（未开通仍具名）|
| `f1j` | `No Pages projects`（空集合）⇒ `ready`（面通了只是没数据，与「没读到」区分）|
| `f1k` | 聚合层：任一服务非 ready ⇒ 顶层不得 READY，且 d1 不被 r2 连坐 |
| `f1l` | workers `not_probed` ⇒ `GAP_CRED`（未读到 ≠ 平台没开）|
| `m2`（变异）| 整表关掉形状尺 ⇒ 帮助文本必须被误算 ready ⇒ 反证 f1g 的绿来自这把尺 |
