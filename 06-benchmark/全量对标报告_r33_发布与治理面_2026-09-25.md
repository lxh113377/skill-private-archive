### 1.1 四条结论

**① 「零治理件 + 零发布面」不是本体系的独特选择 —— 但只有一个对手和我们同形，而它是规范本体。**
11/12 对手有 LICENSE，唯二没有的是 anthropics/skills（0 tag / 0 release / 0 治理件）与本仓。
差异在动机：anthropics 是**规范文档仓**（发布物是 spec 与示例，不走版本）；我们是**私有归档仓**。
⇒ 结论不是"该补 LICENSE"，而是**"本仓的定位决定了发布面形态"**（见 §5 X-2）。

**② 治理件密度与星标再次无关，与"是否对外分发"强相关。**
269,117★ 的 mattpocock 只有 2/5；46,874★ 的 AAS 是 5/5 满配；36★ 的 mycelium 3/5。
满配的三家（spec-kit / AAS / 加 ruflo·mem0 的 4/5）**全部是有 npm/PyPI 分发物的产品仓** —— 与 r31 §1.2① 同向：
**决定工程严格度的是"有没有外部消费者"，不是"多少人点星标"。** 本体系无外部消费者 ⇒ 这条维度上的"落后"是定位的必然结果，**不是缺陷**。

**③ 但有一个子项是真缺陷：版本锚机器不可查。**
本体系把版本写在文本里（技能 frontmatter `version:`、AGENTS 的 `Version: V1.0`、SKILL.md 的 `V10.70.0` 锚点行），
**git 层面 0 tag** ⇒ 无法 `git describe`、无法回答"r31 那次改动落在哪个提交"、回滚定位只能靠翻 `git log --oneline` 的人眼。
对手 12/12 至少 4 个 tag（除 anthropics=0，而它不做发布）。⇒ **本轮 H-2 直接补上**（不是抄 LICENSE，是补可机读锚点）。

**④ ⚠️ 内部矛盾（本轮实测发现，比对手结论更有价值）：我们的门禁把业界标准治理件当散落项。**
受管根 `焚诀` 现被并行会话加了 `CONTRIBUTING.md` / `LICENSE.md` / `SECURITY.md`（mtime 09-25 02:35-03:08），
`handoff.py noise` 实测逐条判 **VIOL 并要求"迁往 _trash（禁止删除）"**。
⇒ 若照门禁建议执行，就会**把三家满配对手都有的标准治理件扔进回收站**；若不执行，noise 门永远红、savepoint 永远过不去。
这不是"门禁正确"或"文件该删"的二选一，而是 **allowlist 缺一条治理件白名单口径**（属 A-project-handoff 的 `common.py` allowlist 面）。
⇒ 本仓不擅动他人在途文件（R269），登记为**待裁定**：由归属会话决定「纳入白名单」还是「本体系刻意不放治理件并写明理由」。

## 6. 事故与自纠登记（本轮）

1. **Edit 两次 `old_string` 不匹配，第三次改用精确替换 + 命中计数护栏** —— 我在收紧断言时两次凭记忆转写文件内容（漏了 `「」` 引号形态、且 t19 参数已被自己改过）⇒ Edit 0 occurrences。
   第三次改法：用 python 做子串替换，**每条替换前置 `count == 1` 硬校验，不等即 ABORT**，避免"替换到多处"或"替换没命中还继续跑"。
   ⇒ 可复用形态：**改自己刚写的文件也要先读回或做命中计数护栏**，别拿记忆当磁盘（R-CURRENT 的微观版本）。
2. **r32 立的规矩当场用上了，且当场抓到自己的旧写法不合格** —— 收紧 JSONL 断言前，t14-t19 全是 `any("关键字" in x ...)` 形态，
   其中 t14 写的是 `any("origin" in x and "1" in x ...)`：**任何含字母 o/r/i/g/i/n 的消息 + 任何含字符 1 的消息就能判"拦住"**，是教科书级虚绿。
   现全部锁专属 token。对照：未变异台账真跑 0 违规（生效侧）+ 污染三种形态逐条被点名（反例侧）。
3. **`stat -c%s` 与 `grep -c` 在 `&&` 链里会把"0 命中"变成"整段未执行"** —— r32 §7.4 登记的坑本轮再次遇到（改 `;` 分隔后正常）。
4. **未夸大的地方**：tags/releases 计数用 `per_page=100`，达 100 的三家（spec-kit/ruflo/mem0/AAS）我全部标 **100+ 触顶**，不当精确值引用。
