## 2. 逐项差距说明

**D-96（P0）：指标只有"值"没有"保质期"，所以源件烂在柜里也照样出数。**
r53 我差点得出"`catalog_grand_chars` 跟 33 轮前的快照比"的结论（后证明是**命名**假阳性），但那件事揭开的是真缺口：
`ratchet_gate.py` 里没有任何地方声明"这个指标多久必须重算一次"。今天没红，只说明**今天恰好跑过**。
对手侧对照：pre-commit 12 行、spec-kit 7 行显式声明节律（cron / timeout-minutes / concurrency / if），
> 取值（节律声明行数与提交日期）：`gh api -H "Accept: application/vnd.github.raw+json" repos/<R>/contents/.github/workflows/<f>.yml | grep -cE '^\s*(cron:|timeout-minutes:|concurrency:|if:\s)'` 逐文件求和；`gh api "repos/<R>/commits?per_page=1" --jq '.[0].commit.committer.date[:10]'`
其余三家 **0 行** ⇒ "多久跑一次"在成熟仓里是被声明的对象，不是靠人记得。
→ 落地 `METRIC_SOURCES` + `METRIC_REFRESH_DAYS`（9/9 逐个声明，债务三态 3 天 = 超一轮即漏跑）+
`source_age_days` + 三态 `face_metric_refresh`：**STALE ⇒ 该指标进 unknown**（陈旧源件不配当现值参与棘轮比对）；
**UNVERIFIED ⇒ 保持原值**（活体扫描类本无源件，判它红等于逼我造一个假源件）；CLI 打印「再生周期」行。
夹具 12 例，含两向（g8 真机必须 0 超期、g2 12 天 vs 预算 3 必须 STALE）与配置形态反例（g5 预算写 0 不得变全员判红、g7 必须 ∈ (1,60]）。
> 取值（夹具与再生周期）：`python 05-exec/r54_refresh_fixtures.py`（12 例全绿）、`python 05-exec/ratchet_gate.py` 末行「再生周期（W-36）：8/9 指标在预算内」

**D-97（P1）：`unknown` 现在混装了两种成因，趋势线读不出来。**
`collect_metrics` 把"计算抛异常""值类型不对""源件超期"三种情况都塞进同一个 `unknown` 列表 ⇒
下轮看到 unknown=1 时无法区分是**判据坏了**还是**我漏跑探针**。这两种的处置动作完全相反（前者修代码、后者重跑）。
→ 登记 **W-37**（预算搬进 `inject_ratchet_baseline*.json`，由契约做集合全等，代码只读）与
**W-38**（台账加 `refresh_stale_count` 列，使"漏跑"成为可看斜率的量而非一次性告警）。

**D-98（P1）：证据件存在但入口不可达 = 等于不存在（续款收口）。**
r53 补了证据面导航 19 链接，但**读序清单与六阶段产物地图仍是纯文本路径**（`memory/07-next-steps.md` 这种写法点不动）。
本轮改完：README 全文 **24 个链接**（19 指向 06-benchmark）、**死链自检 0**。
对手对照：AAS 一份 README 50 个文件链接；我方此前对 60+ 份证据件的可达链接数为 **0**。
> 取值（README 可发现性）：`gh api -H "Accept: application/vnd.github.raw+json" repos/addyosmani/agent-skills/contents/README.md | grep -c '](.*\.(json|md|yml))'`；我方 `python 05-exec/r53_handles_fixtures.py` 之 h8/h9（含死链自检）

**D-99（P2，方法论）：不能用"声明了节律"推断"在维护"。**
pre-commit 声明最密（12 行）却 39 天没有提交；spec-kit 声明 7 行且昨日刚提交；
> 取值（三列并列，禁单指标下结论）：上一条命令的节律行数 + `gh api "repos/pre-commit/pre-commit/commits?per_page=1" --jq '.[0].commit.committer.date[:10]'` = 2026-08-17；判定列复现见 `06-benchmark/ci_evidence/`（r32 原始件）
AAS/anthropics 零声明但提交很新（09-23 / 09-24）⇒ 我 r33 那套"治理件密度与星标无关"的结论要再加一条：
**治理件与节律声明也无关活跃度**，看维护状态必须同时看 (a) 最近提交日期 (b) 自动化节律 (c) 作业是否真产生判定
（r32 的 `steps=0` 配额失败是第四坑）。本报告已按三列并列呈现，不再单指标下结论。
