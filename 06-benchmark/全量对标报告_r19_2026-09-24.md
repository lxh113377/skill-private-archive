### 2.2 N10 · 技能正文的计数断言不在任何内容级门禁面上（本批最硬）

- **对应本体系模块**：`焚诀/eval/verify_checks/*` + 各端注入用 `SKILL.md`/`AGENTS.md` 文本面。
- **可借鉴**：焚诀自己的 C16（把「mtime 新鲜」升级为「内容 == 真相源」）——本项只是把它外推一个面。
- **本轮动作**：新建 `05-exec/claim_truth_scan.py`（三族：端数/枚举/退役声明、裸技能计数、版本号引用；
  R241 历史留痕行豁免；R247 真相源不可读 ⇒ exit 2 禁判零失真），首跑 **10 条候选**。
  整改建议登记为转焚诀 **C31′**（不代改 `eval/`）。

### 2.3 N11 · description 只判「双要素」，不判「把流程写进描述」

- **对手口径**：N-A `skill-anatomy.md` 原文——"Do not summarize the workflow — if the description contains
  process steps, the agent may follow the summary instead of reading the full skill."
- **实测**：本体系 **24/166** 命中（如 `ai-video-homework-pipeline` 的「图生视频 → TTS 配音 → … → 合成」链、
  `chaoshi-web-deploy` 的「①Cloudflare…②GitHub…」）。这些正是「agent 照摘要执行」的高危形态。
- **本轮动作**：判据已并入 `description_baseline_scan.py`（`PROCESS_RE`）+ 夹具 3 例（含正当描述不误伤反例）。
- **待办**：24 条的逐条改写属 `rule_editor` + 派生件重建面 ⇒ 与 r18 N1 目录税整改**合并到同一窗口**做（双倍成本规避）。

### 2.4 N12 · 只有事后批量扫描，没有写时拦截

- **对手实物**：N-E 除 `check-rule-conflicts.py` 外另有 `hooks/check-rule-conflicts-on-write.py`，
  即「改规则文件的**那一刻**报冲突」，而非攒到下次审计。
- **本体系现状**：三门禁（mirror/noise/evolution）+ r18 四工具全是**批量事后**；且 r18 已实证三仓无 `pre-commit`
  （R270 因此把「自动修复」改为主动前置）。⇒ 写时面在本体系是**结构性缺位**，不是漏配。
- **建议**：列为 P2（触发条件 = 决定是否给受管根补装 pre-commit 的那次裁定；与既有「暂不补装」裁定绑定）。

### 2.5 N13 · 对手把契约写成版本化 schema 族，我们写成散文

- **对手实物**：`schemas/aas-v1/` 12 份（含 `doctor-result`、`recovery-plan`、`selection-evidence`、`plan`）。
- **本体系现状**：`06-benchmark/` 9 份基线 JSON 各带 `schema` 字符串（`cumulative-drift-scan-v1/v2`、
  `rule-conflict-scan-v1`、`claim-truth-scan-v1`…）但**无一处可机检的契约**；本轮已出现真实后果：
  drift 扫描升 v2 后，若沿用 v1 的下游读者会静默读不到 `excluded` 字段。
- **建议**：P1-B′（缩小版）——先给**本仓 9 份基线**落一份 `schemas/r19/` 契约 + 一份校验器（不碰焚诀），
