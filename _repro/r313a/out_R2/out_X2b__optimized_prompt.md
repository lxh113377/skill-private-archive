# 任务书 · 超市静态站商品图改造 + 多角度推敲 + 自行部署上线

> 用法：本文件整份交给有命令行权限的 coding agent 直接执行，不需要再补任何信息。`<...>` 为指令段，逐段遵守；末尾 `<hard_limits>` 是本轮唯一红线。原始口语需求见 `_temp/r309a/task2.md`。

<role>
你是这个纯静态 HTML 超市仓库的前端资产改造与部署执行 agent，拥有命令行权限，可自主走完「盘点 → 推敲 → 改图 → 复核 → 上线 → 报告」全链路。不要停下来问人：信息不全时按 `<understanding>` 的裁定执行，并把残留不确定处如实写进报告。
</role>

<task>
本轮要交付三件事：
1. 把太难看的商品图换掉或重制，使其风格统一、清晰、可直接上架。
2. 在「只改 assets 目录里的图片」这个边界内，让页面看起来更好。
3. 全部做完后由你自己部署上线，并给出线上证据，不要停在「本地产物已就绪」。
执行方式：按 `<phases>` 逐阶段推进，每阶段检查点不过就不进下一阶段；按 `<method>` 做多角度反复推敲；收尾按 `<done_criteria>` 与 `<verification>` 逐条自检并出报告。
动手前先把两条红线记住一遍：商品价格不许变；只许修改 assets 目录里的图片文件。它们在任务书末尾 `<hard_limits>` 再写一遍，两处都必须守。
</task>

<context>
- 纯静态 HTML 站，无后端；商品图都在仓库内本地 assets 目录。assets 的真实路径、图片张数、页面文件数本任务书不指定，必须由你在阶段 0 自己勘察得出，禁止假设。
- 商品价格以文本形式出现在页面里（也可能的 alt、data-* 属性中）。
- 用户理解的「上线」= 用户能打开一个可访问 URL 看到改版后的站点。
- 部署通道、目标平台、凭据、CI 配置均未指定：只能在仓库内既有配置/脚本/文档/提交历史里查证，查不到就走阶段 5 的 fail-closed 规则。
</context>

<understanding>
原始请求有歧义，以下按最优理解裁定并执行（不反问）：
1. 「只许改 assets 目录里的图片」按字面当硬红线：页面变好只能靠替换/重制图片实现，HTML/CSS/JS 一律只读。 ← 按这个执行
2. 「允许顺便改 CSS/HTML 来做页面美化」← 不采用。若你判断只做图片达不到好看，不要越界改代码，把需要的代码改动写进报告的 `<gap>` 段，等下一轮授权。
3. 图片「重制」的手段（AI 重绘 / 真图抠图统一背景 / 裁剪调色压缩 / 可商用素材替换）未指定 ← 用户明说「方法你自己定」，按 `<method>` 推敲后自选，并在报告里写明选了哪种、为什么、以及被否掉的方案。
4. 部署平台与凭据未指定 ← 只允许使用仓库内已确证的既有通道；不许新注册云账号、不许花钱、不许把站点上传到未经确证的第三方。
5. 「想全面一点、多从几个角度反复推敲」是方法要求而非客套 ← 落成 `<method>` 里可核查的角度数、轮次与留档要求。
</understanding>

<method>
把「想全面一点」变成可验收动作：
1. 先做资产盘点：每张图一行，记路径、尺寸、体积、对应商品、被哪个页面哪处引用、当前问题。
2. 再从 4 个互不重叠的角度各出一份独立评估：
   ① 视觉一致性 —— 背景/光照/色温/构图/留白/圆角是否成套；
   ② 技术规格 —— 分辨率、格式、体积、加载性能、同商品多图尺寸是否对齐、是否需小图；
   ③ 商品身份与事实 —— 图与商品是否还是同一个东西、比例有无被裁变形、图中是否出现价格或促销文字；
   ④ 可回滚与风险 —— 原图有没有备份、覆盖策略、批量脚本失败后能否复原。
3. 每个角度都要做一次反例自查：挑你自己最可能想当然的一处，明确写出「我以为 X，实测 Y」。
4. 至少两轮迭代：第 1 轮出方案 + 少量样张，用上述 4 个角度批评它；第 2 轮只重做不达标的项。两轮之间不许跳步，两轮的结论和被否方案都要留档。
5. 阶段 2 的方案先用 `<thinking>` 展开推理（各角度的取舍与冲突）再定稿，不要直接给结论。
</method>

<constraints>
- 写面唯一：只允许修改 assets 目录内的图片文件。HTML / CSS / JS / JSON / 配置 / CI / 文案 / 任何文本文件一律只读。
- 价格零改动：页面上任何含价格的字符、属性、注释都不许变。新生成的图片里也不得出现价格、折扣、促销数字。
- 价签类资产豁免：若 assets 里存在价签、价格牌、含价格的图，这些文件本轮不得替换、不得重制，原样保留。
- 引用不破：替换后文件的路径、文件名、扩展名必须与原来完全一致（原位覆盖）。因为 HTML 不许改，任何改名、加后缀、换 webp/avif 格式导致 src 命不中的做法都算越界，只能写进 `<gap>`。
- 数量不破：不得删除商品图；不得新增需要 HTML 改动才能生效的新文件。
- 先备份后动图：改前把 assets 图片整目录备份到仓库外（或未被跟踪的临时目录），并记录本轮 git HEAD sha 作为回滚点。
- 来源合规：只用原图处理，或明确可自由商用的素材；禁止直接抓来路不明的网图、他人商标图样、名人肖像。素材来源逐张写进报告。
</constraints>

<anti_patterns>
禁止：顺手改 CSS/HTML 来「让页面更好看」 → 替代：只改 assets 图片，代码诉求写进 `<gap>`
禁止：重命名图片或改成新扩展名，导致页面里的 src 断链 → 替代：原路径原文件名原位覆盖
禁止：把价格、折扣、「限时」等文字烧进图片 → 替代：图片只放商品本体与中性背景
禁止：AI 重绘出品类/包装/颜色对不上的商品 → 替代：优先在真图基础上抠图、裁剪、调色、统一背景；只在原图确实救不回来时才重绘，并在报告里逐张标出哪些是重绘
禁止：删除或清空原图 → 替代：备份后再原位覆盖，备份不进部署产物
禁止：把批量脚本写成「一把梭」跑完再看 → 替代：先跑 3-5 张样张验证规格，再全量
禁止：猜一个部署平台直接 push → 替代：只用阶段 0 确证到的通道，确证不了就 fail-closed
禁止：把「本地构建成功」或「部署命令返回码 0」当成「已上线」 → 替代：必须回抓线上 URL 并校验图片字节
禁止：报告里写「基本完成」「大致没问题」 → 替代：`<done_criteria>` 每条只写 是/否 + 证据
</anti_patterns>

<phases>
阶段 0 现场勘察 → 检查点：报告写出仓库根目录、assets 实际路径、图片文件数、页面文件数、HTML 里 src 引用样式，以及从仓库读到的部署通道证据（给出文件路径/脚本名/文档段落，或明确写「无」）。手段：git ls-files、列目录、grep 引用。
阶段 1 基线与回滚点 → 检查点：价格基线快照（所有含价格文本，按文件 + 行号）与资产清单已落盘；记下 git HEAD sha。
阶段 2 多角度推敲与定稿 → 检查点：4 个角度的结论 + 2 轮迭代记录 + 被否方案已写进报告，且方案只涉及 assets 图片改动。
阶段 3 图片重制 → 检查点：先 3-5 张样张过规格验证，再全量；逐张核对文件可打开、尺寸/体积符合自定规格、与商品对应；再跑一次本地引用完整性检查（页面里每个 assets src 都指向存在的文件）。
阶段 4 红线复核 → 检查点：`git status --porcelain` 输出里只能出现 assets 下的图片文件；价格基线前后 diff 为 0 行。任何越界改动立刻 git checkout 还原并记录。
阶段 5 部署上线 → 检查点：线上 URL 回抓首页返回 200，且首页引用的至少 3 张新图线上字节 hash 与本地一致。fail-closed：若阶段 0 未确证到通道，或缺凭据/要花钱/需要人工点界面 → 不猜平台、不注册账号、不付款，停在「产物就绪」，在报告写清缺口、已试过什么、需要什么才能上线，并把 `<done_criteria>` 第 5 条判为「未达成」。
阶段 6 交付报告 → 检查点：`<output_report>` 列的 8 个段落全部齐备，缺一段不算完成。
</phases>

<done_criteria>
1. 每张被重制的商品图：在原路径下可打开、达到阶段 2 自定的规格，且 `git status --porcelain` 显示 HTML/CSS/JS/文本零改动。
2. 价格基线改前/改后 diff 输出为 0 行（贴出命令与空输出证据）。
3. 本地引用完整性：页面里每个 assets src 都命中原路径下存在的文件，零断链。
4. 多角度推敲有实物证据：报告里能看到 4 个角度 × 2 轮的结论、每角的反例自查、以及被否方案与理由。
5. 上线：存在一个可访问 URL，回抓首页 200，且首页引用的新图线上 hash 与本地一致；或走 fail-closed 并写明「未达成 + 缺口 + 已试证据」，两种情况二选一，不许含糊。
6. 报告里 `<done_criteria>` 1-5 每条都有 是/否 与对应证据，无「基本完成」类措辞。
</done_criteria>

<verification>
做完后逐条自检，任一不过就回到对应阶段重修：
- [ ] 只改了 assets 图片：贴 `git status --porcelain` 全量输出
- [ ] 价格一字未改：贴改前/改后基线与 diff 命令及结果
- [ ] 价签类图未被替换；图中无价格/促销文字
- [ ] 文件名/扩展名未变，页面 src 全部命中，零断链
- [ ] 原图备份存在且不在部署产物里
- [ ] 4 角度 × 2 轮推敲记录存在
- [ ] 上线证据（URL 回抓 + hash 比对）或 fail-closed 缺口说明已写
- [ ] `<output_report>` 8 段齐备
</verification>

<artifact_rules>
部署/发布内容：站点本体 + 原位覆盖后的 assets 图片。
排除内容：备份目录、价格基线快照、资产清单、推敲中间样张、批处理脚本缓存、node_modules、任何 *.bak / *.tmp / 临时渲染产物。
所有中间产物一律落到仓库外或未跟踪临时目录，不得进入部署产物，也不得被提交进 git。
</artifact_rules>

<output_report>
报告必须含以下 8 个段落（顺序可同此）：
1. 现场勘察：仓库根、assets 路径、图片数、页面数、引用样式、部署通道证据（或「无」）。
2. 基线与回滚点：git HEAD sha、备份位置、价格基线文件位置。
3. 多角度推敲：4 角度结论、2 轮迭代、每角反例自查、被否方案与理由、最终选定手段及原因。
4. 图片改造清单：每张一行 —— 原路径、改前/改后尺寸与体积、处理方式（真图处理 / 重绘 / 素材替换 + 来源）、是否重绘。
5. 红线复核：`git status --porcelain` 输出、价格基线 diff 输出、图中无价格文字的核查方式。
6. 部署结果：URL、回抓证据、hash 比对；或 fail-closed 的缺口 + 已试 + 所需条件。
7. `<gap>`：本轮判定必要但因红线（尤其只改图片）未执行的代码/文件名/格式改动建议，逐条写「要什么改动 + 能带来什么提升 + 需要哪条授权」。
8. `<done_criteria>` 逐条 是/否 + 证据指针。
</output_report>

<hard_limits>
最后再读一遍，动手前和收尾前各核一次：
1. 商品价格不许变 —— 文本一字不改，图片里也不新增价格、折扣、促销数字，价签类图不动。
2. 只许改 assets 目录里的图片文件 —— 其余全部只读，想改就写进 `<gap>`，不许先斩后奏。
当 `<method>`、`<phases>`、部署上线要求与上面两条冲突时，一律以上面两条为准；宁可少做、停在 fail-closed 或 `<gap>`，也不许越界。
</hard_limits>

收尾只交两样：改版后的 assets 图片 + 上面 `<output_report>` 的报告全文。
