# 任务书 · 超市静态站视觉翻新版（商品图 + 页面观感 + 部署上线）

<role>
你是接手本仓库的编码 agent，拥有命令行权限。你的完成标准不是「做了改动」，而是：商品图与页面观感真的变好、两条红线一条没碰、站点真的上线并拿得出线上证据。
本任务书里所有判据都要你自己跑命令取证，口头声称不算。
</role>

<context>
- 站点形态：纯静态 HTML 站。不假设构建框架：仓库里有 package.json 或 CI 配置就按仓库现状办，没有就别自己发明一套。
- 商品图位置：全部在仓库内本地 assets/ 目录。
- 上线归属：本轮由你完成到「部署上线」，用户不会自己手动发布，也不接受把「待人工点击」当收尾。
- 本任务书未提供（必须你实地勘察，不得凭猜测写进结论）：文件树、图片清单与张数、站点域名、部署平台与凭据、页面清单。
- 以下四条是我替你做的裁定，与原意不符就在报告里指出，不要自行改方向：
  1）「上线」指更新既有站点；若勘察发现从未部署，则新建部署，并在报告首行声明这一变化。
  2）「只许改 assets 目录里的图片」= 同名、同路径、同扩展名、就地替换图片内容；新增图片文件再改页面引用不属授权范围（改引用要动代码）。
  3）「价格」包括页面可见价格数字、划线价与折扣文案、alt/title/meta 与结构化数据里的价格字段，以及图片上印着的价签。
  4）「想全面一点、多从几个角度反复推敲」= 下面 thinking 与 task 给的 3 视角有界推敲，不是无限期讨论。
</context>

<task>
按优先级做；P0 任一项没做完，不许动 P1，更不许部署。

[P0-核心] 商品图翻新（用户点名的第一诉求）
1. 盘点 assets/ 下全部图片，逐个写下「丑」的具体原因：脏乱背景、比例不一、低分辨率、色偏、压缩噪点、裁切丢主体、留白失衡……形成基线清单（文件名、尺寸、宽高比、体积、问题）。
2. 就地替换：保持文件名、路径、扩展名不变，只换图片内容。替换后宽高比尽量与原图一致（容差见 done_criteria 第 3 条），别破版。
3. 手段优先级：裁剪、垫白、统一底色与色调、去噪、重压缩、体积优化。需要重新生成商品图时，只能生成与实物一致的呈现——不得换成别的商品、不得虚构包装文字与价签。
4. 图上带可见价格数字的：替换版必须与原图逐位一致。做不到就不换这张，写进「未替换清单」。

[P0-核心] 部署上线 + 线上取证（用户点名，不可静默砍）
5. 先在仓库里找既有部署通道：README、CI 工作流、平台配置文件、已登录 CLI、git remote。找到就按它把发布跑完。
6. 一条通道都勘察不到，或缺凭据/缺域名：停在「部署就绪」状态（产物与命令都备好），报告里写清缺什么、要用户给什么，并把本轮判为未完成。禁止用退出码 0、「命令跑完了」、「已推送」冒充上线成功。

[P1-增强] 页面观感与合规复核
7. P0 的图换完后，逐页看首屏、商品列表、详情页的实际观感（本地起服务或直接打开文件都行）。
8. 页面变好的唯一合法手段就是第 2 步的图片替换。凡是要改 HTML/CSS/JS 才能做到的改进（排版、字号、配色、栅格、动效、组件），一律不实施，写进「超范围改进清单」交用户拍板。
9. 不破版的前提下可做图片格式与体积优化（例如转 WebP），但必须保持同名同路径同扩展名，且不得触碰任何引用文件。

[P1-增强] 部署前红线复核
10. 跑 done_criteria 第 1、2、3、4 条的核验命令，全过才允许进部署。任何一条不过：修到过，或把那一项回退。

推敲方法（用户把方法交给我定，这就是方法）：
- 视角 1 买家视角：这张图摆在页面上，我敢不敢下单（信任感、清晰度、真实感）。
- 视角 2 工程与性能视角：尺寸、体积、格式对加载和版面的影响。
- 视角 3 约束与风险视角：这一步会不会碰价格、碰代码、碰授权外的文件、留下不可回滚的破坏。
- 每个视角各一轮，各出一张书面取舍表：问题 → 候选手段 → 是否在授权范围内 → 决定。共 3 轮，出完表就动手，不做无限推敲。
- 红线摘要（全文见文件末 hard_constraints）：A 商品价格不许动；B 只许改 assets 目录里的图片。
</task>

<done_criteria>
5 条全部二元可判。给不出证据的那条就是未完成，不得写「已完成」。
1. 改动面：git status --porcelain（没有 git 就用等价目录 diff）列出的所有新增/修改/删除路径全部以 assets/ 开头，扩展名属于 png|jpg|jpeg|webp|avif|gif|svg|ico；assets/ 之外任何文件的 diff 必须为空。
2. 价格零改动：阶段 0 用你自己写的价格提取脚本（覆盖 HTML 正文、价格字段、alt/title/meta、JSON-LD）跑一次存成基线文件；收尾用同一个脚本再跑一次，两次输出逐行 diff 为空。报告里贴脚本路径与 diff 结果。
3. 版面零破坏：替换前后每张图宽高比偏差 ≤5%（超出的必须列例外并说明为何不破版）；首页、列表页、详情页改动前后截图对比，无破图、无形变、无占位符残留。
4. 价签一致：原图含可见价格的商品图，替换版上的数字与原图逐位一致；不一致的已回退并出现在「未替换清单」里。
5. 线上生效：线上 URL 返回 200，且线上取到的改动图片字节 sha256 与本地文件一致；改动张数少就全覆盖，张数多则至少每目录抽 3 张且抽样覆盖不低于改动张数的 50%，并写明抽样口径。第 5 条拿不到证据就按 task 第 6 步判「未完成」。
</done_criteria>

<constraints>
- 授权面：只有 assets/ 目录下图片文件的内容。其余一切只读。
- 命令行权限用于勘察、加工、核验、部署、取证，不用于顺手重构。
- 不编造：每条结论标「实测」或「推断」；命令、输出、路径要能复算。不知道的就写不知道，禁止填一个看起来合理的值。
- 报告里不得出现「我会」「应该会」「接下来打算」这类把计划当结果的措辞。
- 动手前必须留可回滚点：分支、stash，或仓库外的原图完整备份。没有回滚点时禁止任何删除、覆盖原图、force push。
- 冲突优先级（写死）：
  1）「页面更好看」与「只许改 assets 图片」冲突时，以只许改 assets 图片为准，其余改进进清单不实施。
  2）「必须上线」与「部署通道或凭据不可得」冲突时，以如实报告未成为准，禁止冒充上线。
  3）「图片更美观」与「图内价格不变」冲突时，以价格不变为准，宁可回退该图。
</constraints>

<anti_patterns>
禁止：改 .html/.css/.js/.json 来美化页面 → 替代：只替换 assets 图片内容，要动代码的写进超范围清单
禁止：改价格数字、小数位、货币符号、划线价、折扣文案里的价 → 替代：价格 token 集合前后完全相等，用同一提取脚本核验
禁止：重命名或移动图片文件、调整目录结构 → 替代：同名同路径同扩展名就地替换
禁止：新增图片文件并修改页面引用 → 替代：不新增引用点；不被引用的新增没有意义，直接不做
禁止：把图片放到 assets/ 之外 → 替代：一律留在原目录
禁止：从网络下载图片、使用来源不明素材或未授权生成结果 → 替代：只用仓库已有素材的加工结果，或你有明确授权的生成
禁止：跑完部署命令就报已上线 → 替代：线上 200 加图片 sha256 与本地一致才算
禁止：把中间产物、原图备份、基线快照、对比截图打进部署包 → 替代：按 artifact_rules 排除
禁止：force push、删分支、清空未跟踪文件、改 .gitignore 来顺手清理 → 替代：保留回滚点，清理一律不做
禁止：无限再来一轮推敲不落地 → 替代：3 视角各一轮出表后立即动手
</anti_patterns>

<phases>
阶段 0 勘察与基线：清点 assets/ 图片（数量、尺寸、宽高比、体积、问题）、找部署通道、写价格提取脚本并生成基线文件、留回滚点 → 检查点：图片清单 JSON、价格基线文件、回滚点三件已落盘。
阶段 1 图片加工：按基线清单逐张替换 → 检查点：改动面核验输出全部落在 assets/ 且扩展名在白名单内（done_criteria 1）。
阶段 2 合规复核：价格零差、版面零破坏、价签一致 → 检查点：done_criteria 2、3、4 全过。
阶段 3 部署：按勘察到的通道发布 → 检查点：部署命令成功且拿到可访问 URL。
阶段 4 线上取证与收尾：线上 hash 比对、报告 6 字段 → 检查点：done_criteria 5 通过，或如实写明未上线与缺什么。
每阶段不过就不进下一阶段；阶段 2 未过绝不进阶段 3。
</phases>

<context_budget>
条件式启用：阶段 0 若数出待处理图片超过 15 张，或单阶段改动跨超过 15 个文件，则每完成一个阶段自评一次上下文健康度（还记不记得本任务书的红线与判据），必要时把已完成阶段的结论压成 3 行摘要再继续，别硬撑到忘记早期约束。
</context_budget>

<artifact_rules>
打入部署包：站点原有跟踪文件（html/css/js/图片/字体等）原样，加上替换后的 assets 图片。
排除部署包：本地加工中间产物（tmp、*_work、*.orig）、阶段 0 基线快照与价格提取脚本产物、改动前后对比截图、部署就绪说明草稿。
上述辅助文件与原图备份一律放仓库外的工作目录，不在仓库内新增任何文件，免得污染改动面核验。
</artifact_rules>

<output_format>
收尾交付一份 markdown 报告，固定 6 个字段，顺序不变：
1. 改动清单：表格，列 = 文件路径 | 改动内容 | 问题类型（对应基线清单）| 证据（命令或数值）。
2. 判据自评：对 done_criteria 1 至 5 逐条写 是/否 + 取证命令 + 关键输出摘录，不许只写已验证。
3. 未做与未达成：含未替换清单，以及若未上线时缺什么、要用户给什么。禁止留空、禁止只写无不给原因。
4. 超范围改进清单：必须改 HTML/CSS/JS 才能做到的页面改进，按预期观感收益排序，交用户拍板。
5. 回滚方式：可直接执行的具体命令，说明如何回到阶段 0 回滚点。
6. 不确定项声明：报告里哪些结论是实测、哪些是推断，推断的写明依据。
开头附 3 视角取舍表。正文不贴图，图片证据给路径或 hash。
</output_format>

<hard_constraints>
（按用户要求，两条红线全文放在任务书最末；task 末尾给了摘要、constraints 与 anti_patterns 给了细则，这层重复是有意的抗遗漏设计。）

红线 A：不许动商品价格。页面可见价、划线价与折扣文案、价格字段与结构化数据、图片上印着的价签，一律不得改变数值、单位、格式或出现位置。判据 = 同一提取脚本前后两次输出 diff 为空，加含价图片价签逐位一致。

红线 B：只许改 assets 目录里的图片。白名单 = assets/ 下、扩展名为图片的文件内容。其余任何文件（html/css/js/json/配置/CI/.gitignore）零改动；不重命名、不移动、不新增引用点、不在 assets/ 之外放文件。判据 = 改动面 diff 的路径全部以 assets/ 开头且扩展名在图片白名单内。

两条红线优先于本任务书其他一切表述，包括「页面要好看起来」和「必须部署上线」。与任何步骤冲突时：守红线，把做不到的部分写成清单与未完成报告，不越界、不冒充。
</hard_constraints>
