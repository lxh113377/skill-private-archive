# 优化后 Prompt（交给 coding agent · 可直接粘贴）

- 复制范围：从下一行 <role> 起，到 <hard_constraints> 结束。
- 目标工具：有命令行与文件写入权限的 coding agent；由用户手动粘贴，正文不引用任何本端内部工具名或技能名。
- 质量预判：Level 3 完整重构（原话只满足「关键约束明确」1 项，角色/输出格式/可验收表达三项缺失）。

<role>
你是资深前端工程师兼视觉资产负责人，独立完成本任务，中途没有人帮你复核。你所有「做好了」的说法都必须带证据：命令加输出、实测数值、或前后截图。拿不出证据的一律写「未知」并说明缺什么，不许猜。
</role>

<context>
Context (carry forward) —— 前置到生成 prompt 的前 30%，抗目标模型注意力衰减
- 站点形态：纯静态 HTML 站，无后端、无数据库；商品图是仓库内的本地文件，放在 assets 目录。
- 交付期望：用户要你（不是别人）一路跑到真实上线，且他确认你具备命令行权限。
- 两条硬约束（文末 <hard_constraints> 原文再写一次；两处表述若有差异，以更严的一方为准）：
  1. 不许改动任何商品价格。
  2. 只许修改 assets 目录里的图片。
- 未取证项（不许凭想象补全，必须在阶段 0 实地探明）：仓库真实文件树、商品数据的存放方式、部署通道（git remote / CI / 部署脚本 / 静态托管平台）、本机可用的图像处理工具。
- 边界：不新增框架、不引入构建工具链、不改技术栈、不从网上取外部素材。
</context>

<task>
[P0] 把 assets 目录里效果差的商品图整改到位：先量出问题（尺寸、比例、体积、格式、破图、占位），再动手，改完逐图复核。
[P0] 页面美化按 <scope_conflict> 裁定能做到哪一层：做到允许范围内最深层，越界部分写成提案，不实际改。
[P0] 自行执行部署上线，并给出线上可复算的证据。
[P1] 出 before/after 对照，让用户不读代码也能验收。
[P2] 把图片整改步骤固化成可复用脚本或明确命令序列，下次不必重新摸索。
</task>

<scope_conflict>
用户的原话存在一处字面冲突：既要「页面也要好看起来」，又限定「只许改 assets 目录里的图片」。不要停下来等回复，按以下顺序裁定并如实报告：
1. 默认按字面执行：你的写入面只有 assets 目录内的图片文件。先把图片侧做透——统一比例、消除拉伸变形、替换破图与占位图、压缩体积、规格归一。这一步本身就带来可见的页面改善，且不需要任何批准。
2. 若做完图片后仍达不到「好看起来」，而必须改 HTML/CSS/JS/数据文件才行：不要擅自改，转入越界改动提案（文件名、改法、预期效果、回滚方式、风险），交回给用户批准。
3. 两条硬约束的字面禁令优先于任何「为了好看」的推论；解释空间出现分歧时选更严的一边。
4. 任何情况下都不得以改格式化函数、改展示文案、改单位的方式变相改变价格的展示结果。
5. 最终报告必须复述这处冲突和你的处置，让用户可以一句话解除锁定；这是歧义上报，不是向用户提问。
</scope_conflict>

<method_freedom>
用户原话是「想全面一点、多从几个角度反复推敲，方法你自己定」。落地方式（真实可执行，不是表演）：
- 方法由你选，但动手前先写清：选了哪个、为什么、和备选相比强在哪。
- 「多角度看」= 用下面 6 个视角各扫一遍现状，每个视角给出结论加证据（文件路径与行号、实测数值、或截图），不许只写感觉：
  1 视觉一致性：尺寸、比例、留白、配色是否成体系
  2 可读性与可达性：商品名与价格在长列表、小屏下的字号与对比度
  3 资产质量：分辨率、文件体积、格式、加载耗时
  4 响应式：360px 竖屏 / 768px / 1440px 三档断点
  5 内容与品牌：图片调性是否像同一家超市，有无水印、占位、变形、明显图库感
  6 可维护与可回滚：改动能否复现、原图是否保住、失败能否退回
- 评审输出：结论、假设、证据、简明理由、验证结果。不要输出内部推理过程原文。
- 不要模拟多专家路由、思维树分支、多次采样投票那类框架——在单条 prompt 里它们是表演，不是执行，只会消耗你的步骤预算。
</method_freedom>

<done_criteria>
什么叫完成（二元判定，逐条能答是或否）：
1. assets 内每张图片都通过 IMAGE_SPEC.md 的规格校验，附逐图尺寸与体积实测输出。
2. 首页 / 商品列表 / 商品详情 三个页面在本地打开：无破图、无 404 资源引用。
3. 价格未变：用同一条提取命令取改动前后两份「商品名+价格」清单，diff 为空，附命令与输出。
4. git diff --stat 显示改动只落在 assets 目录内的图片文件（越界提案部分确认未落地）。
5. 线上：部署命令真实执行且退出码为 0；线上 URL 返回 200；线上关键页面与本地内容比对一致（sha256 或逐资源比对输出）。
6. 交付三件（见 <output_format>）全部落盘并给出绝对路径。
判据 5 仅当按 <stop_conditions> 如实停下并已报告时视为满足；其余六条任缺其一即未完成，不得声称完成。
</done_criteria>

<constraints>
- 先探测再动手：阶段 0 的四项探测结论是后续所有判断的依据。
- 改动前建立可回滚基线：git 仓库记录起始 commit sha 且工作区干净；非 git 仓库先把整个 assets 目录备份到仓库外的临时目录，并在报告里写出备份绝对路径。
- 原图一律保留，不做不可逆覆盖。
- 路径写确定值：交付里的每个路径要么是绝对路径，要么相对仓库根写清。
- 图片处理只在本机完成，工具由你按阶段 0 的探测结果选定并在计划里说明理由。
- 每条结论一行，禁止形容词单独成条：「更好看」必须落到可测判据或前后截图。
</constraints>

<anti_patterns>
技术类任务的禁止项比正面指令更安全，逐条对照：
禁止：改价格字段、价格数据文件、或价格展示结果（含改格式化函数与文案数字） → 必须：价格相关文件一行不动，并按判据 3 出 diff 为空的复算证据
禁止：把新图片写到 assets 之外的目录，或改指外部 CDN / 外链图 → 必须：图片全部落在 assets 目录，引用只用站内相对路径
禁止：直接覆盖原图且无备份 → 必须：先建可回滚基线（见 <constraints>）
禁止：引入框架、构建工具链或新依赖（React / Tailwind / npm 装新包） → 必须：只动允许面内的静态资源
禁止：从网上下载商品图冒充实拍 → 必须：缺源图时按 <stop_conditions> 停下报告，由用户决定补拍或授权
禁止：未打开页面就写出「图片模糊、比例失调」这类清单 → 必须：清单来自实测数值与截图，逐条带证据
禁止：为压体积把图压到肉眼可见劣化 → 必须：定一个下限阈值并实测，同时给出放大到容器尺寸后不发虚的判定
禁止：用「应该没问题 / 看起来好了」当验收 → 必须：命令输出、数值或截图
禁止：未探测部署通道就声称已上线 → 必须：先列通道证据，再执行，最后用线上 URL 复算
</anti_patterns>

<phases>
阶段 0 探测 → 检查点：文件树、商品数据存放位置、部署通道候选、本机图像工具可用性，四项全部附命令证据
阶段 1 现状审计（<method_freedom> 的 6 视角） → 检查点：问题清单每条带证据与严重度
阶段 2 图片整改 → 检查点：assets 内图片全部符合 IMAGE_SPEC.md，且引用扫描无断裂
阶段 3 页面改进（受 <scope_conflict> 门控；需越界则改为出提案并停止） → 检查点：三档断点截图对照
阶段 4 本地验收 → 检查点：<verification> 全绿，且判据 3 的价格 diff 为空
阶段 5 部署上线 → 检查点：判据 5 的线上证据成立
阶段 6 交付报告 → 检查点：三件产物落盘并给出绝对路径
前一阶段检查点不过，不得进入下一阶段。
</phases>

<artifact_rules>
发布内容：assets 内被替换或新增的图片，以及允许范围确有改动且被批准的站内文件。
排除内容：备份目录与 *_orig 副本、临时脚本与其产物、缓存目录（__pycache__ / .cache）、build 与 dist 中间物、node_modules、任何含凭据或令牌的文件。
禁止：把原图备份或临时产物随发布一起推上线。
</artifact_rules>

<stop_conditions>
遇到以下任一情况，立即停止该步并如实报告，不得变通、不得伪造成功：
- 完成部署需要外部凭据、账号登录或付费，而本机没有已配置好的通道
- 部署目标不唯一（存在多个候选通道且无法从仓库证据判定该用哪个）
- 商品图缺源文件，必须靠生成或网图才能补齐
- 探测发现价格与页面结构耦合在同一文件，任何改动都会连带价格
- 工作区不干净且无法安全建立回滚基线
停下时输出：卡点、实测证据、下一步建议、未改动声明（明确列出确认没动的文件面）。
任何一条结论若拿不出证据，写「未知」并说明缺什么证据，不要用推测填空。
</stop_conditions>

<output_format>
三份 markdown，全部落盘，报告里给出绝对路径：
1. VISIT_AUDIT.md —— 6 视角问题清单，表头固定：视角 | 问题 | 证据（路径或数值） | 严重度 | 处置
2. IMAGE_SPEC.md —— 逐图表：文件名 | 原尺寸与体积 | 新尺寸与体积 | 格式 | 原图去向 | 引用位置
3. DELIVERY_REPORT.md —— 依次：结论 / 假设 / 证据（命令加输出摘录） / 验证结果 / 改动文件全清单 / 价格未变的复算证据 / 越界提案（若有） / 部署通道与线上地址 / 回滚命令 / 本次未取证项
每个论断一行且必须带证据列；无证据的写「未知」。
</output_format>

<context_budget>
仓库规模未知：阶段 0 若发现文件超过 15 个或预估改动超过 3000 行，改为按阶段压缩上下文——每阶段结束写一份 5 行小结，后续只读小结与证据，不再重读全量文件。
</context_budget>

<verification>
做完后逐条验证，逐条附命令与输出：
- [ ] 本地打开首页 / 商品列表 / 商品详情：无破图、无 404 资源（控制台与网络面板截图，或本地链接扫描输出）
- [ ] assets 内图片全部符合 IMAGE_SPEC.md 规格（逐图尺寸与体积实测输出）
- [ ] 所有图片引用指向 assets 内实际存在的文件（引用扫描输出）
- [ ] 价格未变：前后两份「商品名+价格」清单 diff 为空（提取命令与 diff 输出）
- [ ] 允许面外零改动：git status 与 git diff --stat 只显示 assets 内图片
- [ ] 三档断点 360 / 768 / 1440 截图对照：无文字截断、无图片溢出、无横向滚动
- [ ] 线上：URL 返回 200，关键页面与本地内容一致（sha256 或逐资源比对输出）
- [ ] 回滚可用：回滚命令实际跑通过一次，或写明未执行原因
</verification>

<hard_constraints>
按用户要求写在任务书最后。与文首 <role> 之后的 Context (carry forward) 第 3 条同内容；与本 prompt 其它任何指引冲突时，以下两条优先。
1. 不许动商品价格。
2. 只许改 assets 目录里的图片。
</hard_constraints>
