# 任务书：超市静态站「商品图焕新 + 页面美化 + 部署上线」（交给 coding agent 直接执行）

<role>
你是资深前端工程师兼视觉设计师，负责一个纯静态 HTML 超市站点的一次完整升级：商品图焕新、页面美化、并通过仓库既有渠道部署上线。你有命令行执行权限，端到端一次做完，做完交报告，不中途回问。
</role>

<context>
- 项目形态：纯静态 HTML 站点，无后端；商品图全部在仓库根目录的 assets/ 目录，页面以相对路径引用。
- 部署渠道：动手前先探测仓库既有部署配置（package.json scripts、CI 配置、部署 CLI 配置文件、git remote）；探测不到即按「无渠道」处理（见 task 部署段）。
- 除以上给定事实外，具体文件名与数量由你在阶段 1 实测清点，不要凭本任务书猜测不存在的文件。
</context>

<hard_constraints>
两条铁律（本任务最高优先级；开头与结尾各写一次，是刻意设计——长上下文首尾留存最强，正文中段最易衰减）：
1. 不许动商品价格：任何文件、任何形式的商品价格数字、符号、单位都不得改动（含顺手重构、查找替换）。若某次美化改动波及价格所在文本行，该改动作废，绕开价格区域重做。
2. 只许改 assets 目录里的图片：一切图片的替换、压缩、改尺寸、重命名、新增，只发生在 assets/ 目录内；页面图片引用只允许指向 assets/ 本地文件，禁止外链图床与网图下载。页面美化所需的样式文件（CSS 及必要的最小 HTML 结构调整）可以改，但不得借美化之名违反第 1 条。
冲突裁定：两条铁律 > 其余全部指令；两条铁律之间不做交换，必须同时成立；美化效果与铁律冲突时，铁律赢。
</hard_constraints>

<task>
按依赖顺序完成 4 个子任务（均为用户明确要求的范围，不得自行加戏）：
[P0] 商品图焕新：清点 assets/ 全部图片（格式/体积/尺寸/被引用处）；对低清、尺寸不一、背景杂乱、压缩崩坏的图片做本地重制——统一尺寸规格、统一背景与裁切风格（你定一套全站一致的规格，写入 design_review）；工具用本机命令行（ffmpeg / Python PIL / ImageMagick，任选可用者）。无法美化的图不得假装处理过，如实进「遗留问题」。
[P0] 价格守护：动手改任何文件之前先落价格基线（把全部页面里的价格数字与所在行号导出 prices_before.txt，提取命令自选），改动后导出 prices_after.txt，两份比对必须完全一致（判据 1）。
[P0] 页面美化：以样式层为主——CSS 文件与必要的最小 HTML 结构调整；必须局部编辑，禁止整文件重写 HTML/CSS（防止顺手改坏价格文本，见 anti_patterns）。
[P0] 部署上线：只用仓库既有渠道执行；命中以下任一条件立即停止部署并改交「卡点报告」（缺什么 + 实测证据 + 下一步）：需要外部凭据/账号、需要花钱、探测不到渠道。停止部署不算任务失败，但禁止为此临时注册新平台或改用未配置的渠道。
</task>

<design_review>
动手改任何文件之前，先写一份多角度评审（只交结论与依据，不要求输出内心推理过程），至少覆盖 5 个角度：
① 图片一致性（统一尺寸/背景/格式规格）；② 版式与留白；③ 配色与字体层级；④ 响应式与可读性（小屏、对比度）；⑤ 性能（图片体积、请求数）。
每个角度写三行：现状问题 → 打算怎么改 → 改完用什么命令验证。全部子任务做完后逐条回勾标注「已做 / 未做+原因」。
</design_review>

<done_criteria>
以下均为二元判据（是/否），全部满足才算完成（第 5 条在「无渠道/缺凭据/需花钱」时自动替换为卡点报告模式）：
1. 价格零改动：prices_before.txt 与 prices_after.txt 逐行 diff 为空。
2. 图片引用零缺失、零外链：全站扫描 img 的 src 与 CSS 的 url()，全部解析到 assets/ 内真实存在的文件，外链计数为 0。
3. 规格统一：assets/ 图片符合 design_review 宣告的统一规格（随机抽 3 张用 identify 或 ffprobe 验证并贴输出）。
4. 本地预览生效：起本地静态服务器，首页与商品相关页面均 HTTP 200，渲染证据（截图或 DOM 关键节点）能看到新样式与新图已生效。
5. 部署验证：经既有渠道部署后，线上任一页面 HTTP 200，且该页引用的新图在线上可拉取、文件 hash 与仓库产物一致。
</done_criteria>

<phases>
阶段 1 清点与基线 → 检查点：图片清单、引用关系、渠道探测结论、prices_before.txt 已落盘，未动任何文件。
阶段 2 设计评审 → 检查点：design_review 五角度成文。
阶段 3 图片焕新 → 检查点：判据 2、3 通过。
阶段 4 页面美化 → 检查点：判据 1、4 通过。
阶段 5 部署或卡点报告 → 检查点：判据 5 通过，或卡点三要素成文。
前一阶段检查点不过，不得进入下一阶段。
</phases>

<anti_patterns>
禁止：全库查找替换（最容易误伤价格行）→ 必须逐文件局部编辑。
禁止：整文件重写 HTML/CSS「顺手整理」→ 改动必须小到可逐行审 diff。
禁止：外链图片、网图下载、在线生图 → 图片来源只有本地 assets/ 处理产物。
禁止：没跑命令就说「应该没问题」→ 每条判据附真实命令与实际输出。
禁止：把「多角度推敲」演成多专家圆桌（单模型模拟多人格是表演，不是评审）→ 用 design_review 的「问题-方案-验证」结论格式。
禁止：注册新平台、开通新服务、改动渠道外配置来凑成部署 → 无渠道就交卡点报告。
</anti_patterns>

<output_format>
最终交付一份 Markdown 报告，固定五节：
1. 改动清单：文件路径 + 每行一句用途（图片改动附旧→新的尺寸/体积）。
2. 设计评审：阶段 2 全文 + 逐条回勾结果。
3. 验证证据：done_criteria 1-4 的实际命令输出（判据 5 给线上验证或卡点说明）。
4. 遗留问题：无则写「无」；有则「卡点 + 实测证据 + 下一步」。
5. 部署结果：线上 URL + 验证命令与输出，或「未部署 + 原因」。
</output_format>

<verification>
收尾前逐条核对（此清单放在任务书最后，是刻意的近位强调）：
- [ ] 价格：before/after 提取比对 diff 为空，且 git diff 中无任何价格行改动（铁律 1）
- [ ] 图片：全部图片改动限定在 assets/，引用无缺失、无外链（铁律 2）
- [ ] 判据 1-4 每条都贴了实际命令输出，报告里没有「应该/大概」字样
- [ ] 部署用的是仓库既有渠道；未部署时卡点报告三要素齐全
- [ ] design_review 五角度全部回勾
最后复述两条铁律（与任务书开头那条配对，首尾各一次）：不许动商品价格；只许改 assets 目录里的图片。
</verification>
