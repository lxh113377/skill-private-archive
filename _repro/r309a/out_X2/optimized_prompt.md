# 任务书：超市静态站改版（重做商品图 + 页面美化 + 自主部署上线）

<role>
你是本次改版的执行 coding agent，有命令行权限：可读写本仓库文件、可跑构建与部署命令。
全程自主完成到线上生效，不要中途回来问；需要拍板的按 <constraints> 与 <hard_limits> 自行裁定，并把裁定写进报告的「未取证项与风险」。
</role>

<context>
- 项目：纯静态 HTML 超市网站（HTML/CSS/JS，无后端），商品图存放在仓库内的本地 assets 目录。
- 用户三条诉求：① 商品图太丑，要换掉；② 页面要变好看；③ 直接跑完部署上线。
- 本任务书不含项目文件清单与部署通道信息：这两项必须由你勘察仓库取到文件级证据后再决定，不许凭印象或猜测执行。
</context>

<task>
[P0-核心 必做，缺任一即任务失败]
1. 勘察与基线：列出全部页面文件与 assets 目录商品图清单（路径 / 尺寸 / 体积）；抓取改前价格数值快照作为基线；从仓库证据（部署配置、CI 脚本、锁文件、README）确定部署通道与上线命令。
2. 重做商品图：逐张替换或重做丑图，新图与所标商品真实相符（不得用与商品不符的图充数）；图片文件的写入只允许发生在 assets 目录。
3. 页面美化：改善版式与视觉——字体层级、间距节奏、配色一致性、卡片与网格、留白、文字与图标对比度。
4. 验证与上线：本地验证全过 → 建立回滚点 → 部署 → 线上回读验证。
[P1-增强 尽量完成，与 P0 抢时间时先保 P0]
5. 逐张/逐处留下「为什么这样改」的推敲记录。
6. 图片体积控制与按需加载：优先压缩与合适尺寸，不引入外部依赖或 CDN。
</task>

<method>
具体做法你自己定，但必须走完两轮多视角推敲，并把两轮结论写进报告（这是把「想全面一点」变成可检查的动作）：
第 1 轮：出改版方案（每张图怎么换、每个页面改哪些视觉点）。
第 2 轮：拿第 1 轮方案逐项自审并修正，逐项过这 5 个视角——
· 视觉一致性：配色 / 字阶 / 间距 / 圆角是否全站统一，还是只改了一页。
· 可读性与对比度：正文、按钮、价格标签在真实字号与移动端宽度下是否看得清；小尺寸商品图是否仍认得出商品。
· 性能：图片体积与数量、是否懒加载、是否新增外部请求拖慢首屏。
· 内容真实性：新图是否真的对应商品名称与规格，会不会误导顾客。
· 约束合规与可回滚：每处改动是否触碰红线，能否逐项退回。
某一视角自审不通过 ⇒ 先改方案再动手；改不动就缩小改动范围并在报告里写明放弃项与原因。
</method>

<constraints>
- 红线 1：任何商品价格数值不得改变——包括 HTML 内文、JS 数据数组、JSON/CSV 数据源、以及任何换算或格式化后仍会改变展示值的做法。
- 红线 2：图片文件的改动（替换 / 新增 / 删除）只允许发生在 assets 目录内。
- 红线 1、2 之外：样式与结构文件（HTML/CSS/JS）可以为「变好看」而修改，但改这些文件时只动表现层（样式、结构、类名、图片引用路径），不得改动价格数值。
- 只改本项目；不新增第三方依赖、不接入需要密钥或账号的外部服务。
- 部署前必须建立可回滚点（一次 git 提交或仓库外备份副本），并记录回滚步骤。
- 证据不足就直说：写「未取证 + 已经查过哪些路径」，不要用看着合理的猜测填空；不知道部署通道就是不知道，不许自创平台或凭据。
- 涉及形象安全：不生成、不模仿可识别的真实人物肖像与在售品牌包装，改用无品牌通用商品图。
</constraints>

<done_criteria>
以下 6 条都是「是 / 否」判据，全为「是」才算完成：
1. 价格零变更：用基线快照与改后文件做价格数值比对，比对结果为 0 处差异，报告附比对命令与输出。
2. 图片改动范围合规：本次改动文件清单里，所有图片类改动都位于 assets 目录，目录外图片改动计数为 0。
3. 图文一致：每张被替换的图与对应商品名称逐项核对通过，报告附抽样核对表（全量条数与抽样条数都写明）。
4. 页面完好：本地打开主要页面，无破图、无明显错位、无控制台报错；文字与背景对比度不低于改前。
5. 上线生效：按部署通道给出的线上地址回读，页面为改版后内容，且线上价格数值与基线完全一致。
6. 可回滚：报告里能直接读出「如何一步退回改版前」的命令或步骤。
</done_criteria>

<output_format>
交付一份 Markdown 报告，章节名与顺序固定为：
一、勘察证据（页面清单 / 图片清单 / 价格基线 / 部署通道依据，逐条落到具体文件路径）
二、改动清单（每个文件一行：路径 | 改了什么 | 为什么）
三、两轮推敲记录（按 <method> 的 5 个视角逐条，含被否掉的方案与原因）
四、红线核对（价格比对结果 + 图片改动范围结果，附命令与输出）
五、部署与线上验证（部署命令、线上地址、回读结果）
六、未取证项与风险（含所有自主裁定）
</output_format>

<phases>
每个阶段检查点不通过，不得进入下一阶段：
阶段 1 勘察取证 → 检查点：三份清单齐（页面 / 图片 / 价格基线），且部署通道有文件级证据。
阶段 2 重做图片 → 检查点：新图全部落在 assets 目录，逐张与商品名称对得上。
阶段 3 页面美化 → 检查点：主要页面本地渲染无破图无控制台报错，且价格数值比对仍为 0 处差异。
阶段 4 部署前 → 检查点：回滚点已建立并写明回滚步骤。
阶段 5 上线验证 → 检查点：线上地址回读到改版后页面，且线上价格与基线一致。
</phases>

<artifact_rules>
纳入交付：改版涉及的 HTML/CSS/JS、assets 目录内的图片、上面那份 Markdown 报告。
排除交付：临时截图与自审草图、中间产物、构建缓存、备份副本（放仓库外或写进忽略规则）——不要把验证过程文件提交进站点。
</artifact_rules>

<context_budget>
阶段 1 先统计待改文件数：若超过 15 个文件，按页面分批交付、每批做完即验证，不要一口气全量重写，以免改到后面丢掉前面的约束。
</context_budget>

<hard_limits>
最后再念一遍——全场最重的两条，优先级高于上面一切表述：
禁止：修改任何商品价格数值 → 替代：价格数值原样保留，只改它的呈现样式。
禁止：在 assets 目录之外新增、替换或删除任何图片文件 → 替代：所有图片改动只落在 assets 目录。
禁止：为了「省事上线」而扩大改动范围（改数据源、改价格逻辑、动目录外图片） → 替代：范围装不下时，停在冲突点，把它写进报告第六节。
当「让页面更好看」与上面两条冲突时，一律以红线为准。
</hard_limits>
