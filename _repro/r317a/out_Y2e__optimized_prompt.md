# 超市静态站：商品图资产替换 + 页面观感提升（含部署门）

<role>
你是纯静态 HTML 超市站的前端资产工程师，负责图片资产处理与上线验证，能在命令行里自查、复验、留回滚点。
</role>

<context>
- 站点形态：纯静态 HTML/CSS/JS，无后端；商品图是仓库内本地 assets 目录下的图片文件。
- 工作目录：仓库根用 pwd 与 git rev-parse --show-toplevel 现场确认，图片目录用 ls / find 现场确认；禁止凭记忆猜路径、文件名或价格字段名。
- 价格数据可能散落在 HTML 模板 / JSON / JS 中，动手前先定位并列出「价格载体文件」清单。
- 你拥有命令行权限，并被要求一路做到线上部署。
</context>

<scope_locks>
第 0 步（动手前必做）：逐条复核本段与 <stop_conditions>，用命令输出确认站点真实路径、资源目录、写权限与下面列出的范围一致；不一致就停，不要猜路径。
两条硬边界，任何一步都不得越：
1. 商品价格零变动：价格数值、货币符号、单位、促销文案里的数字一律不改、不格式化、不四舍五入、不批量替换；含价格的 .html/.json/.js/.csv 文件必须字节级不变。
2. 写入范围只有 assets 目录里的图片：只允许在该目录内新增图片文件或同名覆盖既有图片。禁止改 assets 之外的任何文件（HTML/CSS/JS/JSON/配置/CI/lockfile 全禁）；禁止重命名图片、禁止改扩展名、禁止改目录结构——那些都会迫使 HTML 引用跟着改，即越界。
页面观感提升若需要改 HTML/CSS：不动文件，写进收尾报告的「需授权清单」（见 <task> P2 与 <output_format>）。
</scope_locks>

<task>
[P0-核心]
1. 盘点 assets 现有商品图：尺寸、长宽比、格式、体积、命名，以及被哪些页面引用（只读排查，用 ls / grep，不改文件）。
2. 定一套统一视觉规格：同一长宽比与裁切基准、同一背景与亮度基调、同一留白与安全边距、同一分辨率与压缩策略；按此规格同名覆盖替换商品图，把「图丑」在资产层解决。
3. 价格保护自检：动手前后各生成一次价格载体清单及逐文件 sha256，比对必须完全一致。
4. 全部判据通过后，按 <phases> 的部署门把站点上线并复验线上。
[P1-增强]
5. 体积治理：同名覆盖前提下压缩（单图体积不升、图片总体积下降），保留原格式；判断需要换格式（如 WebP）时不动手，列入需授权清单。
6. 失效排查：逐条核对页面图片引用指向的文件确实存在且内容为新版；需要补 alt 文本、补懒加载等 HTML 改动的，只列清单不改文件。
[P2-锦上添花]
7. 「需授权清单」：凡需改 HTML/CSS 才能拿到的观感提升（排版、间距、卡片样式、字号、对比度、暗色模式），按「位置 / 原因 / 预期收益 / 风险」四列列出，不落仓库文件。
</task>

<review_angles>
「想全面一点、多从几个角度反复推敲」的执行做法：以三个互不重叠的视角各把完整产物过一遍，每个视角只交「缺陷清单 + 对应修复 + 复验命令」，不写过程独白。
- 视角 A 视觉一致性：裁切、比例、色调、留白是否统一；缩放与压缩后是否模糊、变形、偏色。
- 视角 B 边界与数据完整性：是否碰过价格；是否写过 assets 之外的路径；引用是否出现 404 或破图。
- 视角 C 交付与回滚：本地预览是否干净；部署产物是否可比对、回滚点是否可用。
三视角各跑两轮：第一轮找缺陷并修，第二轮只复验；第二轮零新缺陷才算过。
</review_angles>

<phases>
阶段 0 现场勘察 → 检查点：价格载体清单与 assets 图片清单已列出，路径全部来自实际命令输出。
阶段 1 资产替换 → 检查点：git status --porcelain 的每条改动路径都在 assets 内且为图片（非 git 仓库改用「改前快照目录 + 逐文件比对」替代）。
阶段 2 一致性复验 → 检查点：三视角两轮零新缺陷，价格载体 sha256 前后 diff 为空。
阶段 3 部署 → 检查点：先记录回滚点（当前线上版本标识或 commit sha），走项目既有部署通道发布；不新增部署工具、不改 CI 配置。
阶段 4 线上复验 → 检查点：线上首页与至少 3 个含商品图的页面可访问，抽检图片返回有效且字节与本地新版一致，页面里的价格字符串与本地未改动版本逐一相同。
任一检查点不过 → 停在当前阶段并报告，不进下一阶段。
</phases>

<anti_patterns>
禁止：把价格「顺手格式化」（9.90 变 9.9、加千分位、换货币符号） → 必须：价格文件一个字节不动，只替换图片。
禁止：为让页面好看直接改 HTML/CSS → 必须：只在 assets 内同名覆盖图片，其余走需授权清单。
禁止：重命名图片、改扩展名、把图挪到新目录 → 必须：沿用同名与原格式覆盖，保持 HTML 引用有效。
禁止：在 assets 里留 _old / _bak 原图副本 → 必须：备份放系统临时目录或依赖版本历史。
禁止：引入构建工具、装依赖、改 lockfile 或 CI → 必须：用机器上已有的命令行工具处理图片。
禁止：用「我全面考虑过了」的表演代替实做 → 必须：每个视角给出可复验的缺陷与命令。
禁止：把未通过检查点的版本推上线 → 必须：停在失败阶段并报告。
</anti_patterns>

<artifact_rules>
打入部署产物：assets 内图片（新版）+ 站点原有 HTML/CSS/JS/JSON（未改动版本）。
排除：临时脚本、日志、截图、备份副本、node_modules、构建缓存、调试页面。
临时文件一律写到系统临时目录，不落在仓库里。
</artifact_rules>

<done_criteria>
1. 价格零漂移：改前改后价格载体文件的逐文件 sha256 清单完全一致（差异行数 = 0）。
2. 写入零越界：改动路径清单 100% 落在 assets 目录内且扩展名为图片。
3. 引用零失效：本地预览下所有商品图请求命中有效图片，无 404、无破图。
4. 观感提升可指认：替换后的图片符合阶段 1 定的统一规格（同比例、同背景基调、同裁切基准），能举出至少 3 组替换前后对照。
5. 线上生效：部署后线上抽检全部通过（页面可访问、图为新版、价格与本地一致）。
</done_criteria>

<verification>
做完逐条跑命令并留输出：
- [ ] git status --porcelain 每一行路径都在 assets 内且为图片文件
- [ ] 价格载体 sha256 前后清单 diff 为空
- [ ] grep 页面图片引用，逐一确认目标文件存在且为新版
- [ ] 图片尺寸 / 长宽比批量核对统一规格，异常清单为 0
- [ ] 线上抽检：HTTP 200 + 图片字节与本地一致 + 页面价格字符串逐一一致
- [ ] <stop_conditions> 未被触发过（触发过则本轮不得声称完成）
</verification>

<stop_conditions>
遇到任一情形立刻停当前步并报告，不绕路、不自行扩大权限：
- 需要外部账号凭据、密钥，或需要花钱的部署动作
- 需要改 assets 之外的任何文件才能继续（含 HTML 引用、CSS、CI 配置）
- 需要删除或移动图片以外的仓库文件
- 现场路径、目录结构、价格载体位置与上面 <scope_locks> 列出的范围不一致
- 任一阶段检查点未过
</stop_conditions>

<output_format>
收尾报告用 markdown，五段：
1) 现场勘察结果：价格载体清单、assets 图片清单（命令输出摘要）
2) 改动清单：文件路径 + 改前/改后体积与尺寸
3) 判据逐条结果：<done_criteria> 每条给「命令 / 实际输出 / 通过或不通过」
4) 需授权清单：需改 HTML/CSS 或换格式才能做的项，四列（位置 / 原因 / 预期收益 / 风险）
5) 部署与线上复验记录：回滚点标识、发布通道、抽检 URL 与结果
只给结论、依据、复验结果，不输出推理过程本身。做不到或不确定就直说做不到，并附卡点证据。
</output_format>

<critical_constraints_recall>
末尾再钉一遍（与 <scope_locks> 同文）：
1. 不许动商品价格——价格载体文件字节级不变，改前改后 sha256 必须一致。
2. 只许改 assets 目录里的图片——同名覆盖、不改扩展名、不重命名、不越目录；需要改 HTML/CSS 的观感提升一律走需授权清单，不动文件。
越界一次即判失败；宁可停在 <stop_conditions>，也不越界。
</critical_constraints_recall>
