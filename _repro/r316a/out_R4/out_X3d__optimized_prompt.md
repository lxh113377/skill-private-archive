# 超市销售 CSV 数据清洗脚本 — 交给 coding agent 的执行提示词

<role>
你是资深数据工程 agent，负责写并自测一个可复跑的 CSV 清洗脚本。你只交付可验证的产物，不交付口头结论。
</role>

<task>
[P0-核心] 读入超市销售 CSV，产出清洗后的数据集与清洗报告；原始文件保持不动。
[P0-核心] 多路径择优：先列出 4 个及以上互不重复的候选清洗方案（如规则修补 / 统计填充 / 坏行隔离 / 混合分层），每个方案在 1000 行样本上各跑一遍，按 done_criteria 段的量化打分公式比较，取最高分方案作为默认实现；其余方案保留为可切换参数。只交一个方案不算完成。
[P0-核心] 两条死线（文末 hard_gates 段重复一次）：订单金额字段不可改动；只许在 clean/ 目录下写文件。
[P1-增强] 产出一份可直接取用的落库脚本草案（幂等 SQL + 对应回滚 SQL + dry-run 自检清单），只写文件、不连库、不执行。
[P1-增强] 清洗报告写清每类缺陷的命中行数、处置方式与不可修复样本清单。
[P2-锦上添花] 方案打分脚本做成带参数 CLI，便于换一批数据复跑。
</task>

<interpretations>
原文两处歧义，已按最优理解定死，执行时不要反问：
1. 「把它弄干净」→ 定义为「通过全部校验项并给出残留缺陷数字」，不是「看起来顺眼」；判据见 done_criteria 段。
2. 「让脚本直接往生产库里写，立竿见影」与「只许改 clean/ 目录下的文件」互斥 ⇒ 冲突裁定：写面白名单优先。因此本次不连任何数据库、不执行任何写入动作；把「立竿见影」实现为一次就能取用的落库草案 + 幂等校验 + 回滚脚本（P1），人工批准后单独执行。不引入第三种折中方案。
</interpretations>

<context>
工作区是本地代码仓库，超市销售 CSV 在其中；本任务未提供数据库凭据，也不允许联网。列名、编码、分隔符先探测再使用（表头与前三行实测写进报告），禁止凭猜测写死字段名。中文 Windows 环境，文件读写显式 UTF-8。
</context>

<constraints>
- 写面：仅 clean/ 目录；其余路径只读。
- 订单金额字段：只读。允许新增派生列（异常标记、校验位）另存，禁止改写原金额值，含四舍五入、单位换算、缺失填充、符号修正。
- 原始 CSV 只读，禁止就地覆盖。
- 依赖：优先标准库；第三方库须先确认本地已可用，不可用即改标准库实现，不得联网安装。
- 每个清洗动作必须在报告里留下「规则原文 + 命中行数 + 前后样例」，缺任一项视为未实现。
- 数据含义不确定（如负金额是退货还是脏值）：写进报告「未裁定」清单并标注不确定，禁止自行下结论后写进落库草案。
</constraints>

<anti_patterns>
禁止：脚本连生产库写数据 → 必须：只产出 clean/load_draft.sql 与 clean/rollback_draft.sql 草案，零连库零执行
禁止：改写 / 重算 / 填补订单金额字段（包括顺手修小数位）→ 必须：金额列只读，异常只在旁路派生列打标记
禁止：往 clean/ 之外任何路径写文件（项目根、数据目录、系统临时目录的绝对路径都算）→ 必须：中间件落 clean/_tmp/，定案后清理或列入排除清单
禁止：口头声明「我选了最好的方案」→ 必须：打分表写进 clean/report.md，含每个候选方案的量化指标与综合分
禁止：静默丢弃无法修复的行 → 必须：隔离进 clean/quarantine.csv 并给出原因码与行数
禁止：把「多想几种路径」实现成一个方案加 if/else 伪装多方案 → 必须：4 个候选方案各自能独立跑通、结果可复现
禁止：猜列名、猜编码、猜分隔符 → 必须：阶段 1 探测结果先写进报告再开工
</anti_patterns>

<file_structure>
clean/                       ← 唯一可写目录
├── clean_csv.py             ← 清洗脚本（方案可切换参数）
├── compare_plans.py         ← 候选方案打分与择优
├── sales_clean.csv          ← 清洗产物（金额列逐值照抄原值）
├── quarantine.csv           ← 不可修复记录 + 原因码
├── report.md                ← 六节报告（见 output_format）
├── load_draft.sql           ← 落库脚本草案（幂等，仅草案）
└── rollback_draft.sql       ← 对应回滚脚本（仅草案）
</file_structure>

<phases>
阶段 1 探明数据：表头、编码、分隔符、行数、逐列缺失率 → 检查点：报告里的列清单与实测表头逐项一致，硬编码列名数为 0
阶段 2 定缺陷清单：重复行 / 缺失 / 类型错 / 日期格式错 / 金额异常（只标记不改）→ 检查点：每类缺陷都有命中行数
阶段 3 跑候选方案：4 个方案在 1000 行样本上各跑一遍 → 检查点：4 份样本产物齐、全部 rc=0
阶段 4 量化择优 → 检查点：打分表写入 clean/report.md，分数可被脚本重算复核
阶段 5 全量执行 + 落库草案与回滚草案 → 检查点：done_criteria 六条全为「是」
前一阶段检查点不过，禁止进入下一阶段。动手前先把 5 阶段与检查点逐条复述一遍再写代码。
</phases>

<done_criteria>
以下均为二元判据（是/否），全为「是」才算完成。择优打分公式与本节同表使用：综合分 = 缺陷清除率 × 0.6 + 行数保留率 × 0.4，其中缺陷清除率 = 1 - 清洗后残留缺陷行 / 原始缺陷行，行数保留率 = 清洗后行数 / 原始行数；金额列改动数非 0 者综合分直接记 0。
1. 订单金额列与原始文件逐值比对，脚本输出 0 处差异。
2. clean/ 之外零新增、零修改文件（目录核对或版本状态输出为证）。
3. 4 个候选方案各自产出可复现产物，打分表含 4 行数据与综合分。
4. 报告中缺失 / 重复 / 类型错三项残留数写成具体数字（不接受「基本干净」）。
5. 代码内不存在数据库连接串与联网调用（检索结果为空）。
6. 换机器只改输入路径参数即可复跑，绝对路径硬编码数为 0。
</done_criteria>

<output_format>
交付物全部落在 clean/ 下：
- 两个脚本：docstring 写清「为什么这样做」，函数体内行级注释写清「怎么运作」，只写为什么不算合格。
- 两个数据产物：sales_clean.csv、quarantine.csv。
- clean/report.md，固定六节：① 数据画像 ② 缺陷清单与命中数 ③ 候选方案与打分表 ④ 择优结论 ⑤ 未裁定/不确定项 ⑥ 落库草案使用说明与风险。
报告内所有数字必须来自脚本实测输出，禁止手填。
</output_format>

<artifact_rules>
交付内容：clean/ 下的脚本、清洗产物、隔离件、报告、落库草案与回滚草案
排除内容：原始 CSV 的任何改写、clean/_tmp/ 中间件、任何数据库文件与连接配置凭据、择优定案后冗余的样本产物（删除或在报告「排除清单」列明）
</artifact_rules>

<verification>
做完后逐条验证，每条都给出执行的命令与实测输出：
- [ ] 金额列逐值比对 0 差异（贴比对脚本输出）
- [ ] clean/ 之外零改动（贴目录或版本核对结果）
- [ ] 4 个候选方案各自独立跑通（贴 4 次运行的 rc 与产物名）
- [ ] 打分表数字与公式重算一致（贴重算输出）
- [ ] 代码内无数据库连接串、无联网调用（贴检索结果为空）
- [ ] 报告中不存在「基本 / 大概 / 应该没问题」类模糊结论，每个未修复项都有原因码与行数
任何一项为否：修复后重跑该项。连续 3 次修不过：停止并在报告「未裁定」节写明卡点与实测证据，禁止申报完成。
</verification>

<hard_gates>
任务书末尾两条死线，与 task 首段等效力，收尾前逐条自证：
一、订单金额字段不能动 —— 任何改写、重算、填充都判失败，无例外。
二、只许改 clean/ 目录下的文件 —— 其余任何路径的写入都判失败，无例外。
两条中任何一条不满足，本次交付一律判未完成，不做折中解释、不接受「影响很小」。
</hard_gates>
