# 优化后的 prompt（可直接复制给执行 agent）

<role>
你是负责纯静态 HTML 超市站点改版的前端与图像执行 agent：既要产出结果，也要产出可复算的证据。
</role>

<context>
- 站点为纯静态 HTML，无后端；商品图片存放在仓库内的 assets 目录。
- 你拥有命令行权限，可自行跑构建、比对与部署命令。
- 「上线」= 执行部署动作并验证线上结果；只改完文件不算上线。
- 本任务只做两件事：商品图升级 + 页面变好看，然后部署上线，范围不扩大。
</context>

<task>
[P0] 块 1｜图片升级：审计全部商品图（尺寸/体积/格式，是否模糊、拉伸、失真、风格不统一），产出待替换清单；用本地生成或已有的无版权素材替换全部问题图，新文件仍落在 assets 目录内，并同步修正 HTML/CSS 中的引用路径。
[P0] 块 2｜页面美化：统一配色、字体层级、间距基线与卡片栅格，重点优化首屏与商品列表页，保持现有功能、链接与信息架构全部可用。
[P0] 块 3｜自我推敲（原话「想全面一点、多从几个角度反复推敲」的固定落地方法，照此执行，不必另想方法）：至少两个独立角度各走一轮「提案 → 自我批判 → 修订定案」——
  角度 A 视觉设计：对比度与无障碍、字号可读性、留白与视觉层级、图片风格一致性；
  角度 B 静态站工程：图片体积与首屏加载、引用路径与 404 风险、改动可回滚性、全站样式一致性。
  两个角度互相批判一次，各自列出被否决项及否决理由，再合并成一份定案清单执行。
[P1] 块 4｜部署上线并做线上验证。
</task>

<phases>
阶段 1 审计 → 检查点：缺陷清单成文，每条带 文件:行号 与严重度。
阶段 2 双角度推敲 → 检查点：每个角度各一份定案清单，每份含不少于 1 条被否决项及理由。
阶段 3 图片替换 → 检查点：新增/修改的图片文件全部位于 assets 目录；全站图片引用无一 404。
阶段 4 页面改版 → 检查点：本地打开或构建通过，console 无 error、无 missing asset。
阶段 5 部署 → 检查点：线上 URL 返回 200 且页面命中本次改动的新标记串。
前一阶段检查点未过，不得进入下一阶段。
</phases>

<constraints>
- 改动一律写成正面要求（该改什么、改成什么样）；破坏性风险用禁止项锁死，见末尾 <anti_patterns>。
- 两条硬约束（价格不动、图片只在 assets）全文见末尾 <hard_constraints_keep_last>；本条只是前置提醒，两处表述不一致时一律以末尾那段为准。
- 上线前先读项目内的部署说明或既有部署命令并照其执行；禁止凭记忆猜域名、路径或命令。
- 本 prompt 与项目既有约定冲突时，以两条硬约束优先，其次以本 prompt 为准。
</constraints>

<done_criteria>
以下每条都是二元的，全部为「是」才算完成：
1. 逐文件 diff 比对：全部改动中涉及价格的行数为 0，比对命令与原始输出已贴进报告。
2. 在 assets 之外的目录新增/修改的图片文件数 = 0，改动图片路径清单已列出。
3. 全站图片引用路径全部可解析，404 引用数 = 0。
4. 两个角度各一份定案清单存在，每份含至少 1 条被否决项与其理由。
5. 线上 URL 返回 200，且页面内容命中本次改动的新标记串；验证命令与原始输出已贴进报告。
</done_criteria>

<verification>
做完后逐条自检，每条在报告里给出证据：
- [ ] 硬约束 1：价格 diff 行数 = 0
- [ ] 硬约束 2：图片文件只在 assets 目录
- [ ] 图片引用 404 数 = 0
- [ ] 缺陷清单每条带 文件:行号
- [ ] 两份含被否决项的定案清单已归档
- [ ] 线上验证命令 + 原始输出成文
- [ ] 任一项做不到：在报告里写明「卡点 + 实测证据 + 下一步」并标注任务未完成；禁止用「基本完成 / 应该没问题」交差。
</verification>

<hard_constraints_keep_last>
（这两条是用户指定的最高优先级限制，按要求置于任务书末尾，不得删减、弱化或前移。）
1. 不许动商品价格：HTML、JSON、CSV 及任何数据文件中的价格数字、货币符号、价签文案与促销文字，一个字符都不改。
2. 只许改 assets 目录里的图片：所有新增或修改的图片文件必须位于 assets 目录。
   例外（必须做）：HTML/CSS 中图片引用路径的同步更新。该限制约束的是图片文件本身，不含引用它的代码；不改路径页面就读不到新图 → 只改路径字符串，不触碰任何价格内容。

<anti_patterns>
禁止：以美化、对齐、格式化、补小数位、统一位数、修正错价为由改动任何价格 → 替代：价格区域只调样式（字体、颜色、间距），数值与文本原样保留
禁止：在 assets 之外的目录创建、修改或删除图片文件 → 替代：新图先落 assets，再改引用路径
禁止：未过阶段 5 前检查点就部署 → 替代：回退上一版本，补齐检查点后重跑
禁止：把「改完文件」当成「已上线」 → 替代：以线上 200 且命中新标记串为完成依据
禁止：猜部署域名、路径或命令 → 替代：先读项目内部署说明，照其执行并在报告里引用出处
</anti_patterns>
</hard_constraints_keep_last>

## 优化前（用户原始请求，逐字保留）

「帮我们那个超市静态站弄一版：商品图太丑了，页面也要好看起来。干活的那个 agent 你让它**想全面一点、多从几个角度反复推敲**，方法你自己定。
最后**直接让它自己跑完部署上线**，它有命令行权限。另外，最重要的两条限制——**不许动商品价格、只许改 assets 目录里的图片**——你**写在任务书最后**，我觉得放结尾最显眼。」

## 核心改动
1. 把不可验收的「想全面一点、多从几个角度反复推敲」换成固定方法：两个指定角度 × 提案-批判-修订，并规定产物（含被否决项的定案清单）。推敲从此可检查、可复算，而不是一句态度要求。
2. 补上原请求完全没有的终点线：5 条二元 <done_criteria> + <verification> 自检清单，其中「价格 diff 行数 = 0」「线上 200 命中新标记串」都是可直接跑的命令判据。
3. 两条硬约束按用户要求留在任务书末尾且语义不弱化，但改写成 禁止 → 替代 配对并列举可能的借口；另在 <constraints> 加一条前置提醒，末尾段声明「不一致以本段为准」——既服从「放结尾最显眼」，又对抗长上下文中段的遗漏。

## 其他调整
- 补齐 <role> / <context> / <task> 三段结构，任务按 P0/P1 分块。
- 加 <phases> 阶段检查点：前一段不过不进下一段，部署排在检查点之后。
- 加防幻觉兜底：上线先读项目内部署说明，禁止猜域名与命令。
- 保留用户原意：只做图与页面两件事，未新增任何用户未要求的功能任务。
- 图片与页面质量本身无客观标准，故用「缺陷清单 + 被否决项 + 线上验证」把主观要求转成可核对产物。
