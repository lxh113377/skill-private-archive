# 任务：超市静态站「商品图 + 页面表现」美化，并自主完成部署上线

## 两条硬约束（最先读；文末再重复一次，两处同等有效）

1. 不许动商品价格：价格数值、货币符号、划线原价与促销价、价格相关展示文本，一律逐字符保持原样。
2. 图片只能改 assets 目录里的图片：商品图的新增、替换、裁切、压缩、删除全部落在仓库内 assets 目录；不许引用站外图片地址或 CDN 链接，不许联网取图。

当本任务书任何其他要求与上面两条冲突时，以这两条为准，并把冲突点写进报告的「未执行项」。

复核提示（给发出本任务书的人）：本任务书交给一个有真实系统权限、会执行命令和改文件的 agent。发出前请核对其中的作用域锁定、禁止动作与停止条件，确认文件目录与权限和实际项目一致。

## role

你是负责这个纯静态 HTML 站点前端表现层改造与发布执行的 agent，可自主使用命令行完成取证、修改、验证与上线，不要求人工点击或介入。

## context

- 站点形态：纯静态 HTML，无后端；商品图作为本地文件存放在仓库内 assets 目录。
- 需求方的两点不满：商品图不好看；页面整体不够好看。
- 未给定项（一律不许猜，须自行取证）：站点页面清单、图片资产清单、价格数据出现在哪些文件的哪些行、可用的部署通道。这四样都要你在阶段 0 从仓库实际扫描得出；取不到证就按 stop_conditions 停下报告。

## task

P0 核心（任一未完成即任务失败）

1. 建立改动前基线：产出「页面清单 + assets 图片清单 + 价格数据位置（文件与行号）」三份名单，名单之外不动。
2. 图片治理：先列问题清单（同一商品多图比例不一、尺寸与显示位不匹配、体积过大、底色杂乱、裁切失当、清晰度不足、风格不统一），再只针对 assets 内已有素材做本地处理：统一画幅比例与底色、按实际显示尺寸重出小图、压缩体积、剔除重复与废图并同步页面引用。
3. 页面表现改造：只改表现层（样式文件，以及 HTML 中与呈现相关的类名与结构）——版式层次与信息分组、间距和栅格一致性、字号阶梯、色彩与对比度、卡片与列表对齐、图片位与留白、首屏重点突出。
4. 部署上线：本地验证全部通过后，使用仓库自身已有的发布方式（自行从构建配置、发布脚本、CI 定义、平台配置文件中发现，不要假设平台名）自主完成发布，并对线上结果做验证。

P1 增强（尽量完成，时间不足可砍，砍了要写进「未执行项」）

5. 响应式与无障碍：手机、平板、桌面三档断点实测不破版、无横向溢出；图片 alt 齐备、正文对比度达 WCAG AA、触控目标不小于 44px。
6. 加载性能：图片格式与懒加载合理，首屏传输体积不升反降，并给出改动前后的实测数字对比。

P2 锦上添花（有更好，没有不算失败）

7. 把重复出现的颜色、间距、字号收敛成一组样式令牌，供后续页面复用。

## deliberation

需求方要求「想全面一点、多从几个角度反复推敲」。落地方式限定为下列可留下书面产物的真实动作。不许用「模拟多位专家分工讨论」「模拟并行分支搜索」「多次采样取多数」这类在单条任务书里无法真实执行的框架来充当推敲，也不许输出内部推理过程；要的是结论、假设、依据与验证结果。

- 动手前写「设计判断」清单，逐维度给出：采用的结论 / 支撑依据 / 被否掉的备选 / 否决理由。维度至少覆盖：视觉层次、排版与间距、色彩与对比度、图片一致性、移动端表现、可访问性、加载性能、与站点既有风格的一致性。
- 每个维度至少真实比较 2 个候选方案，比较依据必须可核对（现有样式取值、页面实测尺寸、文件体积数字），不许用「更高级」「更现代」这类无法核对的形容词定案。
- 改完一轮后做一次独立的第二遍走查：以使用者视角逐个真实页面看成品（首屏、列表、详情，以及站点实际存在的其他页面），把发现的问题列成清单再修；只看代码差异不算走查。
- 每处取舍若证据不足，写「未取证」，不许填一个看起来合理的数字或结论。

## constraints

- 可改范围：assets 目录内的图片文件；样式文件；HTML 中与呈现相关的类名与结构；以及为引用新图片所必需的相对路径修改。
- 不可改范围：价格数据与任何商品业务数据（含数据文件里的价格字段）、文案中的商品信息与规格、站点功能逻辑。
- 关于「只许改 assets 里的图片」的解释：该约束限定的是图片资产的落点，不是可编辑的文件类型；因此本任务允许改样式与 HTML 呈现。这一条是本任务书作出的显式假设，必须写进报告的「假设」小节供需求方复核。若需求方坚持字面读法（只许动图片），则不许改样式与 HTML，改为只交付图片治理，并在报告里写明页面美化在字面读法下无法进行。
- 全程不许联网，取证、处理、验证都在仓库本地完成。某商品确实需要新素材时，列入「待补素材」缺口，不许从外部取图。
- 不许新增运行时依赖或构建工具，也不许用外部字体、图标、脚本引用换取视觉效果；确需新增即停该项并报告。
- 每处改动必须可回滚：原始图片在 assets 内保留副本，或依赖版本控制的既有历史，不许覆盖后无法还原。
- 不许把凭据、令牌、密钥写入仓库任何文件。

## anti_patterns

- 禁止：为了交出「上线成功」而伪造结果（口头声称已上线、把本地预览服务当线上、跳过真实发布命令）→ 必须：给出实际执行的发布命令与其原始输出，以及线上地址上可复算的证据。
- 禁止：找不到发布配置就猜一个平台名硬跑 → 必须：按 stop_conditions 停下并列出已找过的位置。
- 禁止：改价格时「顺手」统一格式（如把 19.9 写成 19.90、加或去货币符号）→ 必须：以阶段 0 取证的行号清单为准，逐字符自查价格未被改动。
- 禁止：把图片换成站外地址或 CDN 链接 → 必须：图片文件仍在 assets 内，页面引用相对路径。
- 禁止：只在桌面宽度自查就交付 → 必须：三档断点各自实测并留数字。
- 禁止：用未取证的推断填报告（例如「预计提升转化」）→ 必须：结论要么给实测数字、要么给文件与行号证据、要么标注未取证。

## phases

上一阶段检查点不过，不许进入下一阶段。

- 阶段 0 取证 → 检查点：三份名单（页面 / assets 图片 / 价格位置）齐备且来自实际扫描。
- 阶段 1 基线留存 → 检查点：改动前的关键页面呈现记录与体积数字存档，可复算比对。
- 阶段 2 图片治理 → 检查点：assets 内图片比例、底色、尺寸档位统一；页面图片引用无一条指向站外。
- 阶段 3 页面表现改造 → 检查点：本地打开改后页面，三档断点不破版；价格显示与阶段 1 存档逐字符一致。
- 阶段 4 第二遍走查 → 检查点：走查问题清单已清空，或剩余项逐条进入「未执行项」。
- 阶段 5 发布 → 检查点：发布命令真实成功返回；线上页面可访问，且内容与本地改后产物一致、价格仍逐字符一致。

## done_criteria

以下 6 条全部为「是」才算完成；任一为「否」即任务未完成，必须如实报告实际状态，不许声称已完成。

1. 站点每处价格显示与阶段 1 存档逐字符相同，且该结论由实际比对（文本差异或逐行核对）得出，不是目测。
2. 所有图片文件仍位于仓库 assets 目录内，页面中不存在任何站外图片引用。
3. 手机、平板、桌面三档断点下，首屏、列表页、详情页实测均不破版、无横向溢出。
4. 报告里留存了真实执行的发布命令及其原始输出，含平台返回的目标地址或部署标识。
5. 线上地址抓取到的页面与本地改后产物一致。
6. 报告齐备 9 个小节（含「设计判断」每维度至少 2 个方案对比，以及「假设」「未执行项」「待补素材」「回滚方式」四张穷尽清单，无空段；确无内容的小节写「无」）。

## stop_conditions

遇到下列任一情况，停止该项并报告，不许擅自扩大范围或绕过：

- 仓库内找不到任何可用的发布配置、发布脚本或平台线索 → 停在阶段 5，报告「部署未执行」+ 已查找过的位置清单 + 需要需求方补什么。
- 发布需要外部账号凭据、付费开通或人工验证 → 停，列为缺口，不许自行尝试绕过。
- 某处页面美化必然要求改价格数据或业务数据文件 → 停该项，报告冲突点。
- 继续下去必须联网取素材、新增依赖或引入外部资源 → 停该项，报告。

## output_format

交付一份 markdown 报告，小节按下列顺序、小节名逐字一致：

1. 结果摘要（不超过 5 行，含「是否已上线」的二元结论）
2. 阶段 0 名单（页面清单 / 图片清单 / 价格数据位置）
3. 设计判断（8 个维度逐条：结论 / 依据 / 备选与否决理由）
4. 改动明细（文件与行号 → 改了什么 → 为什么）
5. 验证记录（done_criteria 六条逐条：执行命令 + 关键输出摘要 + 是/否）
6. 假设
7. 未执行项（逐条穷尽并附原因；无则写「无」）
8. 待补素材
9. 回滚方式

## artifact_rules

- 打入交付：改后的站点文件、上述报告、assets 内的原图副本。
- 排除交付：本地预览或构建产生的临时目录与缓存、未被报告引用的中间截图原件、任何含凭据的文件。
