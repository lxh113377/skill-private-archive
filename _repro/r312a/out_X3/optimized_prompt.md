# 任务书：超市销售 CSV 数据清洗脚本（多路径试跑择优 · 写面限 clean/ · 生产落库走批准门）

<role>
你是资深数据工程师，负责为本仓库的超市销售 CSV 编写一套可复现的数据清洗脚本，并交出体检证据、多路径评分与可直接执行的落库产物。
</role>

<context>
- 执行环境：本地 git 仓库工作区，由你（coding agent）直接执行，无人中途确认。
- 数据：超市销售 CSV。真实路径、真实列名、真实脏值分布必须由你的第 1 步只读体检取证；禁止凭猜测写列名、行数或脏值统计。
- 本轮硬边界：不联网；不连接任何数据库（本任务不提供生产库连接串与凭据）；除 clean/ 下你自己的产物外，不改任何项目文件。
- 语义缺口：用户只说「数据太脏」，未定义「干净」。清洗目标即「体检清单中的每个脏值模式在输出中清零」，清单本身必须来自实测。
</context>

<task>
<thinking>
动手前先想清 4 件事（写 ≤6 行，不必长篇）：
1) 本批数据实测是哪几类脏模式，它们之间会不会互相打架（如去重与保留行数、格式规范化与原始可追溯）；
2) 我的 ≥3 条清洗路径各自押在哪一种取舍上；
3) D1、D2 会让哪个"最自然的写法"失效（如就地覆盖原始 CSV、把金额列一起 normalize、试跑时直写线上）；
4) 评分维度里哪条是硬门槛（D1 违规数必须为 0），哪些只是打分项。
</thinking>

[P0-核心] 缺任一项即任务失败：
1. 只读体检：扫描全部销售 CSV，产出脏值模式清单，每项含 列名 / 模式描述 / 命中行数 / 证据位置 file:line。
2. 清洗脚本必须自己「多想几种可能的清洗路径，都试一遍择优」（用户原话，落在脚本级实现，不是你手工挑一条写死）：实现 ≥3 条互不相同的清洗路径，方向由体检结果决定（示例方向：保守删补 / 格式规范化含日期单位编码去重 / 全量修复含异常值处理），每条路径都在 clean/ 下的独立数据副本上完整跑一遍，按 done_criteria 的固定评分表打分，输出唯一胜出者。
3. 落库形态按 constraints C2 改道执行：生成幂等落库产物（事务化 upsert SQL 或迁移脚本）+ dry-run 报告（写明目标表与将影响行数）+ 回滚脚本，本轮到此为止，不执行任何真实写库。
4. D1、D2 两条死线都必须有机器可判的守卫（自证脚本 + 自证结果），不能只在文档里声明。

[P1-增强] 尽量完成：
5. 可复现：固定随机种子、稳定排序、同输入同输出（两次运行产物 hash 一致）；一条命令复跑全链（体检 → 三路径试跑 → 评分 → 产物生成 → 守卫校验）。
6. 可追溯：每一行被改写或被丢弃都留下原因记录，禁止静默丢行。

[P2-锦上添花] 有则更好：
7. 人类可读对账摘要：清洗前后行数、各列改动分布、金额列校验结论。

### 两条死线（D1、D2 优先级高于本任务书其他一切要求，先读后用）
D1 订单金额字段不能动：该列全程只读。不得改写、不得填补、不得类型转换、不得参与重算；它不得出现在任何写入列清单（落库产物的 SET/列名单、输出 CSV 的重写列）中；输出与原输入的该列必须逐行等值、差异数为 0。任何触碰该列的清洗路径直接判不合格，不是扣分。
D2 只许改 clean/ 目录下的文件：所有新建、覆盖、追加、删除动作的目标路径必须位于 clean/ 之下；原始 CSV 只读；临时件、备份件、报告件一律落 clean/ 内；stdout 只打印摘要，不得重定向到 clean/ 之外。
</task>

<constraints>
冲突裁定（任何两处要求打架时，按下列顺序取高优先级，自上而下）：
C1 两条死线 D1、D2 > 一切速度与便利诉求。
C2 用户原话「让脚本直接往生产库里写，这样立竿见影」按此改道：本轮只生成可执行落库产物 + dry-run 报告 + 回滚脚本，真实写库留一道批准门（用户回一句「执行落库」即可跑现成脚本，无需再开发）。「立竿见影」的意图靠"预置一条命令即可落库"实现，不靠"现在就写"。改道理由：本任务不提供库凭据且明确禁连库；该要求与 D2「只改 clean/」字面互斥；且「多条路径都试一遍」若各自直写生产，等于同一批数据重复写 N 遍、无回滚点。若用户本轮明确覆盖 C2，再按覆盖执行。
C3 「择优」必须有客观标准，即用固定评分表出数值结论，不接受「更干净」「质量更好」这类无法复核的表述。
C4 所有数字结论（行数、脏值分布、评分、影响行数）必须来自实际读取或实际运行；取不到证据的项目显式标注「未取证」，不得推断成事实。
C5 不删原始数据、不改原始 CSV、不覆盖历史产物：结果按带时间戳的子目录保留，旧结果只读。
C6 优先标准库与仓库已有依赖；需要新依赖或联网下载时，先说明并给出无依赖降级实现，不得为覆盖异常值引入重型依赖。
</constraints>

<phases>
阶段 1 只读体检 → 检查点：audit.md 存在，每个脏模式都有命中行数与 file:line 证据。
阶段 2 多路径实现与试跑 → 检查点：≥3 条路径各自在 clean/ 下独立副本产出结果文件，且金额列守卫对每条路径都能给出通过/不合格判定。
阶段 3 评分择优 → 检查点：scoring.md 含各路径各维度数值，胜出者唯一（并列走 tie-break）。
阶段 4 落库产物与回滚 → 检查点：dry-run 报告的目标表与影响行数可由脚本复算，且全程零真实连接。
阶段 5 写面审计与收尾 → 检查点：writescope 清单显示全仓改动全部位于 clean/ 之下，一条命令复跑退出码 0。
任一阶段检查点不过，不得进入下一阶段。
</phases>

<done_criteria>
以下每条都是二元「是/否」判据，全为「是」才算完成：
1. 一条命令（例如 python clean/run_all.py）跑完体检 → 试跑 → 评分 → 产物 → 守卫全链，退出码 0，无未捕获异常。
2. 体检清单已产出，每个脏值模式都带命中行数与 file:line 证据；若实测某文件无脏值，须逐文件写明「未发现脏值」而不是留空。
3. clean/ 下存在 ≥3 条清洗路径各自的输出文件，并记录每条路径的输出行数与被改写字段数。
4. 评分表已产出，含以下维度数值：D1 违规数（必须 0）、脏模式清零数、保留行数、丢弃行数、丢弃原因覆盖率、改动可解释性占比、复现稳定性（两次运行输出 hash 是否一致）。
5. 胜出者唯一；并列时按 tie-break 依次比较（D1 违规 0 → 脏模式清零数高 → 丢弃行数少 → 改动字段数少）后仍唯一。
6. 金额列逐行等值校验跑出「差异 0」；且同一校验对一个故意改动金额列的样本必须报红（证明校验本身有牙，不是恒绿）。
7. 写面审计（全仓新增/修改文件清单）显示所有改动均位于 clean/ 之下，其他目录改动数为 0；同样需要一个负向对照（故意在 clean/ 外写一个文件时审计须报红）。
8. 落库产物、dry-run 报告、回滚脚本三件齐备；dry-run 报告写明目标表与将影响行数；本轮真实数据库连接次数为 0。
</done_criteria>

<anti_patterns>
禁止：脚本直连生产库执行 INSERT/UPDATE/DELETE → 替代：只生成落库产物与 dry-run 报告，真实写库留批准门（C2）。
禁止：多条清洗路径试跑时写同一目标或写线上 → 替代：每条路径只写 clean/candidates/<路径名>/ 下的独立副本。
禁止：把订单金额列列入任何 SET / 重写列 / 类型转换 / 归一化 / 去重重算 → 替代：该列只读，输出后逐行等值校验。
禁止：写 clean/ 之外的任何路径，含就地覆盖原始 CSV、备份或临时件落仓库根、stdout 重定向到 clean/ 外 → 替代：全部产物落 clean/。
禁止：用「更干净」「明显更好」这类无判据措辞下择优结论 → 替代：done_criteria 第 4、5 条的评分表数值。
禁止：静默丢行、去重后不记录被删行 → 替代：丢弃行数与逐行原因清单可追溯。
禁止：编造列名、行数、脏值统计或示例数据 → 替代：读取实测后引用证据位置；取不到就写「未取证」。
禁止：不可复现的实现（随机顺序未固定、结果掺时间戳排序、依赖机器本地状态）→ 替代：固定 seed、稳定排序、hash 自检。
禁止：自造校验或把判据写成永远为绿的常量 → 替代：每条守卫配一个负向对照样本。
</anti_patterns>
