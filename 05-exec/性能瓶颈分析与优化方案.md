## 三、关键问题与优化方案（按优先级）

> 统一保证：所有方案**只调整文档/记忆/加载结构，不动任何脚本判据、门禁标记 `[GATE:...]` 字面量、功能代码与验收口径**。P0-1/P0-2/P1-4 属受管根或上游修改，按红线**只登记方案、待授权后经 `rule_editor.py` 执行**；本轮未执行其中任何一项。

### P0-1（收益最大）A-memory-start/SKILL.md 六个 ⚙️ 速查区迁 `references/`

- **现象**：6 个低频速查区占主文件 67%（46,190B），每个会话首轮全额付费。
- **根因**：R251 已识别该风险并立了「区内追加优先 / 迁 references + 主文件留指针」的判据，但既有 6 区尚未执行迁移；其后每周期的补注仍落在主文件（09-19→09-23 又 +64 行）。
- **方案**：按 R251 判据④既有路径——每区迁入 `references/quickref-<主题>.md`，主文件原位留「一行指针 + 触发关键词」（如「命令行/子进程报障 → 先读 references/quickref-cli-pitfalls.md」）。
- **预期收益**：主文件 68.7KB → ~22KB（**-68%**）；每会话首轮省 ~46KB ≈ 2.3 万字符 ≈ 1.2~1.8 万 token。这是全部方案中单笔收益最大的一项。
- **实现方式**：`rule_editor.py` 分区迁移 + `gates` 复跑（mirror/noise/evolution）；C13 门禁锚点与版本历史区**必须保留在主文件**。
- **潜在风险**：① 低频经验命中多一跳 Read（约 1 次工具调用）；② 指针关键词写不全 → 报障场景漏路由。缓解：指针行必须带报错原文关键词（如 `ParserError`/`Executable doesn't exist`），并在 A-get-memory 反哺时回归检查。
- **回滚**：`rule_editor.py undo` + git revert（受管根有完整历史）。

### P0-2 `contract.md`（44.8KB）按「执行面 / 细则面」拆分

- **现象**：复杂任务首轮必读全文；其中 R-CURRENT 现状核验、规则维护工作流等大段属「特定场景细则」，与 ROUTER 场景无关的会话也全额付费。
- **方案**：拆 `contract-core.md`（MANDATORY READ 清单 + 任务分流 + R-CURRENT 强制步骤索引，目标 ≤15KB）+ `contract-rules-*.md` 分卷（R236/R238/R241/R249/R263 等细则全文）；主文件在对应 Step 处留指针与触发条件。
- **预期收益**：复杂任务首轮省 ~30KB ≈ 0.8~1.2 万 token；简单/继续类任务本就不读，不受影响。
- **实现方式**：同 P0-1，`rule_editor.py` + 三门禁；`A-memory-start` 主文件引用路径同步改。
- **潜在风险**：① 强制读清单与实际分卷错位 → 门禁形同虚设；② 多个 R 条目交叉引用断裂。缓解：拆分后跑 `rule_editor.py gates` + 抽 3 条 R 编号全文检索验证引用可达。
- **回滚**：git revert（单次提交完成拆分，原子回滚）。

### P1-3 本项目 AGENTS.md 注入壳（32.9KB，每轮注入）瘦身

- **现象**：平台把 handoff 生成的注入壳**每轮**塞进上下文；其中 `06-已知约束`（大量已闭环 [BUG]/[DEBT] 留痕）与 `08-AC-OBS`（含整段被注释的历史说明）占近半。
- **根因**：`06-constraints.md` 主文件 13,075B 超 4KB，但上游 `handoff.py` 的 `SPLIT_TARGETS` 只注册 07/05 —— 06 无自动拆卷/迁移机制，只增不减。
- **方案（分两级）**：
  - a) **项目侧（授权后）**：按既有「R241 加校正注 + 销账」惯例，把 06 中已闭环条目收敛为「一行状态 + 指向 `05-exec/` 报告的指针」；销账必须逐条对照分卷 partN 已完成条目（P-1 铁律）。
  - b) **上游侧（登记建议）**：`handoff.py` 将 `06-constraints` 纳入 trim/拆卷口径（破坏性，须用户决策）。
- **预期收益**：注入壳 32.9KB → 估 18~22KB；**每轮**省 ~10-15KB（本项目高频会话累计收益仅次于 P0-1）。
- **潜在风险**：销账时误删「当时为真」的历史留痕（违反 R241）。缓解：只加注/加指针、不重写原句；每条销账前对照分卷。
- **回滚**：工作区 git revert；handoff 产物可由 `savepoint` 重生成。

### P1-4 `unified_router.py` 每次调用 1.12s 冷启动无短路（上游焚诀，登记）

- **现象**：两次调用同为 1.12s（基线 0.03s）——即 `direct_hit=true` 的确定性命中也要全额支付 Python + BGE/onnx 模型加载；每轮消息一次。
- **方案（建议，上游实现）**：① direct_map 命中判定前移到模型加载之前（纯文本精确匹配先行）；② 高频场景可常驻服务化（一次加载，进程内复用）。
- **预期收益**：direct_hit 场景每轮 ~1.1s → ~0.1s；按每天 100 轮会话估，省 ~100s/日。
- **潜在风险**：direct_map 与语义路由的边界回归（须跑 `test_router_regression.py` 全量 + `gates`）；改动路由主链路属上游破坏性改动，须焚诀归属会话裁决（R269 只登记不擅动）。
- **回滚**：焚诀 git revert。

### P2-5 门禁套件 8.2s / noise 5.6s（观察项，暂不动）

均为收尾/提交时低频动作，秒级可接受。noise 5.6s 大头是四受管根全量递归，若未来根体积增长可再议「mtime 增量扫描」，当前**不值得**为此增加复杂度。stub-fail 1+3 属已登记 P0 在途债（`07-next-steps.md`），归属会话收口后 gates 仍为 ~8s，与性能无关。

### P2-6 skill 池 153/203 个 SKILL.md 超 4KB（观察项）

单 skill 体积只在**被加载时**付税；平台枚举只列名字与路径（平台行为，项目不可控）。本项目 77 条自建口径的治理（拆卷/合并）已覆盖自建部分；Top 巨型件 `gstack/*`（44~61KB）需先裁定其属自建还是上游，再决定是否入维护范围——**登记待裁定，不预设结论**。

### P2-7 trim-shell 不认「普通 `- 描述`」形态的已完成条目（上游判据盲区，登记）

- **实测**：05 主壳 5,064B 内 12 条 `- 阶段X …（2026-09-14）` 形态已完成条目，`trim-shell` 跑后原样未动（仅 07 报「无可迁条目」）。
- **判断**：与上游已修的 `has_feature_entries`（review 假阴性族）同源——trim-shell 的条目识别未同步「章节式/普通列表」兼容。**非本轮引入，按 R269 登记，归属 A-project-handoff 会话裁决**；本项目侧无动作（split --check 已判 05 主壳为「索引壳，主卷不拆」，无违规）。
