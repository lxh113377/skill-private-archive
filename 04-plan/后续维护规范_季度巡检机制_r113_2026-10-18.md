### 5.3 存档指纹必须被当作断言对象，且被哈希的件要 pin 字节（r298 一手）

两条硬要求，缺一则「clone 可复算」这句是空的：

1. **判据要把交付件里存档的指纹当断言对象**：stored != recomputed 即 FAIL。只现算不比对＝恒通过检查。
   反例（本仓实测，已登记 R298-6）：_repro/r285l/r285_validate.mjs:183 写的是
   evidence_sha256: createHash(...).update(readFileSync(EVIDENCE)) —— 现算现写、从不与存档值比，
   所以它在 clone 里对任何字节漂移都恒绿。它的 [CONSISTENCY] PASS 只覆盖数值字段，**不覆盖证据字节**。
   恒绿比恒红危险：它看起来像验证。
2. **被哈希钉住的件必须 -text pin 住字节**：本仓 core.autocrlf=true，若无 .gitattributes，git 在 clone
   检出时把 blob 的 LF 转成 CRLF ⇒ 存档 sha（对应 blob）与检出文件（工作树）必然不等。实测：
   _repro/r291b2/harness/results/run_raw.json blob=30,312B 而检出=30,583B；_repro/r285l/results/run.json
   同样漂移（80,492 vs 81,854）。修法取 pin 字节（-text），**不取放松判据**（去掉比对＝放弃「证据没被动过」）。
   范围只覆盖被存档哈希引用的件，不动全仓既有行尾（否则一次性改写他人/历史文件，违 D7.2 单写者）。

验收姿势（时序也是判据的一部分）：**必须在提交 .gitattributes 之后再 clone** —— 我第一次测把 clone 建在
提交前，于是测到旧行为、误判修复无效。现读值：git check-attr text -- <证据件> ⇒ text: unset；
新 clone 里 stat 与 git cat-file -s 同为 30,312B；python -B _repro/r291b2/check_r291b.py ⇒ rc=0 且
[CONSISTENCY] PASS（该件的比对是真比对：stored 与 recomputed 两侧都算）。

季度巡检加一条：对每个含 evidence_sha256/expected_sha 的交付件，抽查其判据是「比对」还是「现算」；

### 5.4 检查件必须 import 被检件的字段定义（R289-1 靶 (b) 的条文，r298 补落纸）

理由（一手，r289 我造过两条零判别力的机械化候选）：静态正则扫「谁 import 了谁的字段」必然把无关的
追加语义误判成回归（实测 27 件恒红），而**运行时探针**才有判别力：检查件应直接 import 被检件里的常量/
函数/字段名，名字改了则 import 当场失败 —— 这比抄一份字段清单可靠，因为抄的那份会漂移（本仓「旧注手抄
数字已漂」即同一形态）。

1. 检查件与被检件共享标识符时，走 `import`（或读同一常量件），**不得复制字面量**；复制即第二真相源。

   的 `--dry-run` 双跑（现读末行 [USAGE:BACKFILL] existing=3110 added=0，二次 added=0 即幂等成立）。
3. 若将来要把这类检查做成常驻门，判据形态只能是运行时探针（跑第二遍比行数/比读数），
   不得回退成正则形态（否则又是恒红门，见 R289-1 的否决记录）。

### 3.7 巡检步的两类非绿退出（r217 立）

巡检步的退出码不只有「0 通过 / 非 0 失败」两态；本仓已出现第三种：**非零退出但那是结论**。混淆三者会造出两种反向事故，都已实测：

| 态 | 例 | 计入失败步？ | 事故形态（若分错） |
|---|---|---|---|
| 通过 | rc=0 | 否 | — |
| **结论性非零** | `req6_attainability` 判「阈值在本面算术不可达」按设计退 1 | **否**（run_step 的 ok_rc=(0,1) + conclusion_rc） | 记成失败 ⇒ 诚实结论把整季巡检打成 DEGRADED ⇒ 下轮开始怀疑巡检本身（R211-3 同族「设计内红与真故障红长得一样」） |
| **真故障非零** | `miss_migration` 判红（M1 挪账 / M2 缩分母 / M3 假消失 / M4 守恒 / M5 自洽）、rc=2 输入面不可用 | **是** | 记成结论 ⇒ 造假改善被巡检盖章放行 |

判据写法（新增步时照此选）：**该步的非零码是否表示「被测对象有问题」**。
是 ⇒ 用默认 `run_step(name, argv)`（红就是红）；否 ⇒ 显式传 `ok_rc`，并在步注释里写明非零码的含义。
`conclusion_rc` 字段随产物落盘（steps[].conclusion_rc），事后可复核哪个步当时是结论而非故障。

> 取值：`python -c` 读 `06-benchmark/quarterly/2026Q4/audit.json` 的 `steps[]`，看 `rc` 与 `conclusion_rc` 两列；

## 5.6 引用必须先 grep 取原文（r300 落纸，R295-1 的规矩；含「引用自己写过的话」）

**规矩**：凡在报告/台账/裁决注/纠正注里**引用任何原话**——包括引用别人写的、也包括引用**我自己**上一轮
写过的话、包括写「我上一轮错了」这类自我纠正——都必须先 `grep`/`read` 取到原文**逐字抄录**，禁止凭印象复述。
纠正注里的每一句引文，都要能在跟踪件里被 grep 命中；命中不到，就只能写「我的推断、待证」。

**为什么**（一手，r295）：我在纠正时**虚构了一句不存在的引文**——断言「我 r294 在报告/台账/GM 写的『scoped
复检 mirror-pass ⇒ 那两单现在真的生效了』是过度概括」，而 r294 根本没有报告文件（06-benchmark 无 全量对标
报告_r294*），台账与 commit 652332c 的原话是「九端读的是文件系统而非 git ⇒ blob 全等即传播生效」。我用记忆
造了自己的原话，再据它「纠正自己」。危害在于它**伪装成诚实**：虚假的自我批评比漏掉一条自我批评更难查。
发现路径本身就是这条规矩：把片段丢进 git grep 扫全跟踪件，那句话只命中我本轮刚写的卡。

**同族（四条，都是「动作/结论没有真的到达证据层」）**：r292 的假探针、r292 的空注入、r294 的错名负控、

## 5.7 复验基线必须钉在「特性引入之前」的提交，禁浮动 HEAD（r301 落纸）

**规矩**：凡要证明「我的改动没有改变既有读数」的复验，基线必须取**特性引入前**那个提交/tag 的版本
（如 `git show r299:05-exec/xxx.py`），**不得**用 `git show HEAD:...` —— HEAD 会随我自己的提交前进，
一旦前进，「跟 HEAD 比」就静默变成「跟含特性版比」，于是复验会报出一堆**口径错造成的差异**。

**为什么**（一手，r301）：我该轮给 r114 加 declared 面后又加两处机制修。第三次复验回滚面时，脚本仍按
「`git show HEAD:05-exec/r114_replacement_scan.py` 当基线」写，而此刻 HEAD 已是含 declared 面的 r300b ⇒
回滚输出（--no-declared-inject，无 declared 键）与「基线」比出 **55 行整行差异**。差异逐键一看全是
`declared_*` 键 —— 不是回滚坏了，是我把基线取错了。改用 `git show r299:...`（特性引入前的 tag）后：
**191 行整行 JSON 不一致 = 0**。

**同族**：R293 的「旧矩阵快照当现行事实」、R298 的「读改前旧快照当现行值」—— 都是**取基线/取现状的口径错**，
而这类错的表现恰好是「复验报红」，最容易被读成「改动引入了回归」。⇒ 复验报红时**先怀疑基线的选取**，
再怀疑改动；且基线一律**钉到具体 tag/sha 并写进复验脚本的注释**，让下一个人能一眼看出它钉在哪。

## 5.8 自然语言判据的每条断言必须「双向压样」，单向压样测不出假红（r310 落纸）

**规矩**：凡是拿代码去判自然语言（存在性/一致性/语境类断言），出厂 selftest 必须同时压两个样本——
①一个**明知该红**的坏样例（断言必须翻 0）；②一个**明知该绿**的好样例（断言必须给 1）。只压坏例的判据
测不出「把合规答案判错」的假红；只压好例的测不出假绿。中文场景额外必查两件事：**分词**（`\W+` 在中文里
不切词，整句成一个 token）与**语境窗口**（否定/例外判定只看邻近字符会漏，要扩到整句）。

**为什么**（一手，r308→r309，我自己的尺两次现形）：
· r308 造的 item8 用 `re.split(\W+)` 取词 + `w in prompt or w in log 自身` ⇒ 中文整句成一个 token 且天然在 log 自身
  命中 ⇒ **明知编造的 log 也判 1**（假绿）。实证：跑 `_repro/r309a/old_item8_false_green_proof.py`，旧代码对 bad 例
  跑出 1、good 例也 1（零区分力）。修=字符 bigram、只与 prompt 求交、支撑 ≥50% 才 1，selftest 补 bad⇒0 断言。
· r309 给 item5 加「否定语境豁免」时只窗前 60 字符 ⇒ 校准的好样例「**不引入** Tree of Thought…改用五阶段」被错判
  0（**假红**）。只压坏样例永远测不出这条。修=扩整句（上一句读到命中处）+否定词表补全，双向复压才 PASS。
· 同轮还抓出 item4 **实现与预注册规格不符**（规格=点名红线行位置，实现=任意信号词行）⇒ 出厂样本再补一对
  （约束只在尾部的 naive ⇒ 0；前置+尾部双写的合规 ⇒ 1）才对齐。

**推论（锚题类实验）**：双臂同分不止一种解释——要么文档没用，要么**题面触顶**。判别性题面的出厂检验是
「naive 照字面办必掉分」的构造样本（不是「我希望它掉分」）。`_repro/r309a/calib/` 就是这个出厂件。


## 5.9 静默吞异常是测量系统最贵的 bug；多轮读数报均值±极差（r313 落纸，一手=r312 假表险情）

**规矩 A（catch 必打印 + 合判红灯查）**：任何判据/合判器里 `except Exception` 后**静默给默认值**的代码都禁止存在——
要么打印异常再降级，要么直接 fail-closed。r312 实录：合判器帮助函数名不副实（io_open 实际含 loads）导致双重 loads
抛 TypeError，被裸 except 吞掉 ⇒ 人判四项**静默变 0** ⇒ 打出 base=4 的假表，而 4=机械4/4+人判0/4 **看着完全合理**。
错误数字往往不是离谱的，是自洽的。暴露只因为多问一句「评分件在盘，人判怎么会全 0」。⇒ 硬规则：
① catch 必打印；② 合判表里 human 侧全 0 或全 4 而第三方件明明存在 ⇒ 当红灯查，不管多合理。

**规矩 B（多轮协议）**：锚题类测量**每题 ≥3 轮重复、报均值±极差**；n≤2 的点值一律降级为「观测点」，
禁写成「提升 X%」结论。一手依据（r310/r312）：task2 分出 7/8 vs 8/8（X 捏造段声称），task3 同项两臂都干净
⇒ 「区分」不复现=执行侧一次性噪声；合并均值 +6.67% 全部由单题单项贡献。轮次 2（r313）正是在补这个复现检验。

  自测必双向、自测 FAIL 即停、装载失败必出声。

### 6. 提交面必须被机器对账（r321 一手，本轮连犯两次）

一手：同一会话内两笔提交都出现「消息声称 ≠ 实际入库」。第一笔 `git add --pathspec-from-file=… --pathspec-file-nul=false`
报 **rc=129**（布尔开关不接值）⇒ add 整条失败，但 `git commit -F` 因暂存区还有别的会话留下的件而 **rc=0**，于是消息描述的产出
一个都没进去。第二笔我把「本笔 67 文件」写进消息，实际 **88**（漏算后续 `git add` 把已改的报告/台账并入 + 过程件混入）。
两笔都是**我复算 `git show --name-only` 才发现**的，不是提交时就拦住的 —— 说明「写消息」这一步根本没有判据。

三条规矩（写死）：
1. **逐条判 rc，禁倒推**：`add` / `commit` 任一步 rc≠0 就停；`commit` 在「空增量 + 残留暂存区」上照样 rc=0，是最会骗人的一步（本仓 #36 的具体形态）。
2. **消息里的文件数是被断言的数**：提交后立即 `git show --name-only --format= -1 <sha> | grep -c .`，与消息中写的数字逐字比对；不等则**下一笔具名纠正**，已发布件禁 `amend`/`force-push` 抹痕（r321 两笔都已被 autopush 推走）。
3. **过程件不进跟踪面**：`commit_msg*` / `stage_list*` / `insert_items*` / `gatemap*` 一律落 `.gitignore` 命中的 `_repro/*/work/`；证据件（现算 JSON、判据脚本、报告）才入库。
